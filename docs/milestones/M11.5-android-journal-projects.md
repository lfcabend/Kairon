# M11.5 — Android: Journal & Projects (Gantt & dependencies) — implementation plan

Status: **Accepted — implemented**. Companion to [`../ROADMAP.md`](../ROADMAP.md) (M11.5
acceptance criteria), [`../DESIGN.md`](../DESIGN.md) §2.2/§2.3/§7/§12
(Mobile), and [`../DATA_MODEL.md`](../DATA_MODEL.md). Follows the structure
and conventions of [`M11-android-foundation.md`](M11-android-foundation.md) —
same split-vertical-slice reasoning, same decision-table format.

M11.5 is the second of the three Android slices (M11 → M11.5 → M11.6). Unlike
M11, it needs **no new backend work at all**: `GET /api/v1/sync`'s
`journal`/`project`/`projectTask` change-sets, and every REST endpoint this
plan consumes (`journal`, `project-categories`, `projects`, tasks,
dependencies), were all already built and shipped by earlier milestones
(M3/M4/M5 on the web side; M11 widened `/sync` to cover all four types even
though M11 itself only ever requested `todo`). This milestone is Android-only:
new Room entities/DAOs, new screens, and widening the one `types` param
`SyncRepository` already sends.

*(User decisions locked for this slice, same spirit as M11's own upfront
calls — see §2 for the full rationale on each: journal editing stays a plain
markdown textarea, no WYSIWYG; the Gantt view is read-only bars with no
drag-to-reschedule; Account/About move behind a top-bar overflow menu to make
room for Journal/Projects in the bottom nav; task reordering and board status
changes are tap-based, no touch-drag gestures.)*

---

## 1. Scope

### In

- **Journal**: a date-navigable day view (today's entries, "+ New entry",
  edit, delete), a custom month-grid date nav with has-entry dots computed
  from the local Room cache (no network round trip), and a search screen
  hitting `GET /journal:search` live.
- **Projects**: category-grouped project list (live-fetched, no Room — same
  "small reference set, just refetch" reasoning as the web app's own
  `project_category` treatment), a project detail screen with **List/Tree**
  and **Board** tabs (Room-backed), and a **Gantt** tab — a custom
  Compose-drawn read-only chart (bars, milestone diamonds, dependency arrows,
  today line) composing the Room-cached project/tasks with a live fetch of
  `GET /projects/{id}/dependencies` (M11 D9 — dependencies stay out of the
  sync feed, fetched per project-detail visit).
- A "Depends on" section in the task edit screen (list current predecessors
  with a remove action; an "Add" picker from the project's other tasks) —
  mirrors the web `TaskDependencySection`.
- `SyncRepository` widened to request `types=todo,journal,project,projectTask`
  (every type `/sync` already supports) and fan out upserts/tombstones to
  three new Room DAOs.
- Nav: Journal and Projects added to the bottom nav; Account and About move to
  a top-bar overflow menu to keep the bottom nav at four items (Today, Todo,
  Journal, Projects).
- Tests: Room DAO tests, repository/ViewModel unit tests (MockK/Turbine),
  Compose UI tests for the new screens — same shape as M11 §7's Android test
  table.

### Out (deferred, with what picks it up)

- **Project categories are not Room-cached.** `project_category` isn't in the
  `/sync` feed at all (no soft delete — DESIGN.md §12/DATA_MODEL.md
  conventions) — the Android app fetches `GET /project-categories` live on
  the project list screen, same posture as `Today`/`About` (M11 §6.5's "no
  natural offline need" reasoning extended to a small, cheap-to-refetch set).
- **`task_dependency` is not Room-cached** (M11 D9, confirmed here rather than
  revisited — no soft delete means a changed-since scan can't represent a
  removed edge) — fetched live via `GET /projects/{id}/dependencies`
  whenever a project detail screen opens.
- **WYSIWYG journal editing.** Android edits raw markdown in a plain
  multi-line text field, no formatting toolbar — *user decision* (D1). The
  content still round-trips as plain markdown text, unchanged from what the
  web editor produces/consumes, so nothing about the wire format or storage
  changes; only the *editing experience* is simpler on this platform.
- **Gantt drag-to-reschedule.** The chart is read-only this slice — *user
  decision* (D2); dates are still editable via the task edit screen's
  plannedStart/plannedEnd fields, same as any other field.
- **Drag-and-drop reordering/board-column drag.** Task reordering and status
  board moves are tap-based (a "Move up"/"Move down" affordance and a status
  picker, respectively) — *user decision* (D4). `POST
  /projects/{id}/tasks:reorder` and the status-changing whole-form `PATCH`
  are still used; only the gesture that triggers them differs from web's
  drag.
- **Assisted scheduling / critical path.** Already out of the feature
  entirely (M5 D18) — nothing new to defer here.
- **Offline writes.** Same posture as M11 (D2 there) — every write below is
  online-required, same plain-error-if-offline behavior, no local queue.
- All five assistant features, and the assistant settings screen — M11.6
  (ROADMAP.md), unchanged.

## 2. Decisions locked for this milestone

| # | Decision | Rationale |
| --- | --- | --- |
| D1 | **Journal entry editing on Android is a plain multi-line `TextField` over the raw markdown `content`, with no formatting toolbar.** *(User decision.)* | Compose has no mainstream WYSIWYG-markdown editor the way Tiptap is for web (M3 D1); adding one would be a real new-dependency decision this milestone doesn't need to make to hit its own scope. Storage/wire format is unchanged — `content` is still plain markdown text — so this is purely an editing-UX scope-down, reversible later without touching the backend or the data model. |
| D2 | **The Gantt tab renders a read-only chart**: bars, milestone diamonds (◆), dependency arrows, and a today line, hand-drawn in Compose (`Canvas`/custom layout — no third-party Gantt library exists for Compose the way `gantt-task-react` does for web, M5 D12). No drag-to-reschedule. *(User decision.)* | Building a correct drag-gesture-to-PATCH flow (hit-testing a bar's ends vs. body, a live-updating ghost bar, snap-to-day, then the same whole-form `PATCH` web's `onDateChange` already does, M5 D14) is real, separate UI work from "render the schedule" — scoping the first cut to rendering only keeps this milestone a vertical slice. Dates stay editable via the task edit screen, same field, different entry point. |
| D3 | **Bottom nav holds four destinations — Today, Todo, Journal, Projects — in that order; Account and About move to a `TopAppBar` overflow (⋮) menu**, reachable from every top-level screen. *(User decision.)* | Six bottom-nav items (the literal web-top-nav order) is above Material3's own 3–5 guidance and reads as cramped; Account/About are low-frequency screens (profile, logout, build info) that fit the "secondary, tucked away" overflow pattern most Android apps already use for settings/about, rather than competing for primary nav real estate with the four screens used daily. |
| D4 | **Task reordering and board status changes are tap-based, not drag.** Tree/board rows get a "Move up"/"Move down" action (or a small "Move to…" position picker) instead of long-press drag-to-reorder; a board card's status changes via tapping a status chip that opens a picker of the other three statuses. *(User decision.)* | Touch drag-and-drop (auto-scroll near edges, drop-target highlighting, cross-column drag) is meaningfully more gesture-handling code to get right than the mouse-based `dnd-kit` web already uses, for an interaction the backend already expresses as the same whole-form `PATCH`/`:reorder` calls regardless of how the client triggers them. Tap-based affordances are a smaller, correctness-focused first cut; revisit only if reordering on a real device proves too tedious in practice. |
| D5 | **Journal's calendar "has-entry" dots are computed entirely client-side from the local Room cache** — a `DISTINCT day` query over the synced `journal_entry` Room table for the visible month — rather than a live call to `GET /journal/entry-days`. | Unlike web (which has no local cache to query), the Android app already has every entry synced via `/sync`'s `journal` change-set by the time the calendar renders; querying Room is strictly cheaper and simpler than a second network round trip for data already on-device, and keeps the calendar working offline. |
| D6 | **Search (`GET /journal:search`) is a live network call, not Room-backed.** | Full-text ranking (`ts_rank`, `ts_headline` snippets) is a Postgres-side computation with no local equivalent — same reasoning Today/About already established (M11 §6.5) for "data with no natural offline need," applied here to a case where offline support isn't even meaningful (searching requires the server's index regardless). |
| D7 | **`SyncRepository.sync()` requests `types=todo,journal,project,projectTask`** (every type the backend already supports, M11 §4.2) in one call, fanning upserted rows out to four Room DAOs (`TodoDao` unchanged, plus new `JournalDao`/`ProjectDao`/`ProjectTaskDao`) and deleting tombstoned ids from each. | This is the one line M11's own D3 anticipated ("M11.5 just widens the set it asks for — no backend change needed") — no design decision left to make, just the mechanical extension. |
| D8 | **Three new Room entities** (`JournalEntryEntity`, `ProjectEntity`, `ProjectTaskEntity`) mirror their `*View` wire shapes field-for-field, minus `deletedAt`, following `TodoItemEntity`'s exact precedent (M11 §6.3) — **no entity for `ProjectCategory` or `TaskDependency`** (D-out above — neither is sync-fed, so neither has a Room table). `KaironDatabase` bumps to `version = 2` with `fallbackToDestructiveMigration()` (no real user data exists outside dev/test devices yet, same "whatever's simplest" posture the rest of this app-foundation milestone took). | Consistency with the one Room-entity precedent already in the codebase; a real migration path is unnecessary ceremony before this app has any installed base worth preserving data for. |
| D9 | **Project detail screens (Tree/Board/Gantt) read from Room as the single source of truth**, same as `DayViewScreen` (M11 §6.3) — `ProjectDao`/`ProjectTaskDao` expose `Flow`s the ViewModels observe directly, kept current by `SyncRepository` and by each write's own success response (upserted immediately, no waiting for the next sync tick) — unchanged posture from M11 §6.4, just extended to two more entities. | Reuses the exact pattern M11 already validated; no new architectural idea needed here. |
| D10 | **The project list screen is **not** Room-backed** — `GET /projects` (paginated) and `GET /projects/priority-ordered` are called live, same as `GET /project-categories`. Only a project's **detail** screen (once a specific project is opened) switches to Room-backed reads of that project + its tasks. | The list screen's own data (every project, grouped/sorted) changes rarely enough and is cheap enough to refetch that a live call is simpler than reconciling a paginated/sorted live view against a Room cache that's also being asynchronously updated by `/sync`. Once a project is opened, its own tasks are a bounded, frequently-interacted-with set — exactly the shape Room's already proven itself for with Todo — so that's where the caching investment actually pays off. |

## 3. Data model

**No new migration, no backend changes at all** (confirmed above) — every
endpoint and `/sync` change-set this milestone's Android work consumes
already exists. The only "data model" change is three new Room tables, local
to the Android app:

```kotlin
// core/data/JournalEntryEntity.kt — mirrors JournalEntryView (journal.api), minus deletedAt
@Entity(tableName = "journal_entry")
data class JournalEntryEntity(
    @PrimaryKey val id: UUID,
    val day: LocalDate,
    val position: Int,
    val title: String?,
    val content: String,
    val mood: Int?,
    val createdAt: Instant,
    val updatedAt: Instant,
    val version: Long,
)

// core/data/ProjectEntity.kt — mirrors ProjectView (projects.api), minus deletedAt
@Entity(tableName = "project")
data class ProjectEntity(
    @PrimaryKey val id: UUID,
    val categoryId: UUID?,
    val name: String,
    val description: String?,
    val status: String,
    val size: String?,
    val priorityRank: Int,
    val categoryRank: Int,
    val color: String,
    val startDate: LocalDate?,
    val endDate: LocalDate?,
    val actualStart: LocalDate?,
    val actualEnd: LocalDate?,
    val createdAt: Instant,
    val updatedAt: Instant,
    val version: Long,
)

// core/data/ProjectTaskEntity.kt — mirrors ProjectTaskView (projects.api), minus deletedAt
@Entity(tableName = "project_task")
data class ProjectTaskEntity(
    @PrimaryKey val id: UUID,
    val projectId: UUID,
    val projectName: String,
    val projectColor: String,
    val parentTaskId: UUID?,
    val name: String,
    val description: String?,
    val status: String,
    val isMilestone: Boolean,
    val plannedStart: LocalDate?,
    val plannedEnd: LocalDate?,
    val estimateHours: java.math.BigDecimal?,
    val actualHours: java.math.BigDecimal?,
    val progressPercent: Int,
    val position: Int,
    val createdAt: Instant,
    val updatedAt: Instant,
    val version: Long,
)
```

`KaironDatabase` (D8):

```kotlin
@Database(
    entities = [TodoItemEntity::class, JournalEntryEntity::class, ProjectEntity::class, ProjectTaskEntity::class],
    version = 2,
    exportSchema = false,
)
@TypeConverters(RoomConverters::class)
abstract class KaironDatabase : RoomDatabase() {
    abstract fun todoDao(): TodoDao
    abstract fun journalDao(): JournalDao
    abstract fun projectDao(): ProjectDao
    abstract fun projectTaskDao(): ProjectTaskDao
}
```

`DataModule` gains `fallbackToDestructiveMigration()` on the builder and three
new `@Provides` methods, same shape as the existing `todoDao()` one.

### 5.2 Sync & local cache (D7–D10)

- `SyncRepository.sync()`'s single call becomes
  `syncApi.sync(since, "todo,journal,project,projectTask")`; the response body
  gains `journalEntries`/`projects`/`projectTasks` change-sets (already
  present in the generated model since M11 built the whole `SyncResponse`
  shape) fanned out to `journalDao.upsertAll/deleteByIds`,
  `projectDao.upsertAll/deleteByIds`, `projectTaskDao.upsertAll/deleteByIds` —
  same pattern as the existing `todos` block, just three more `let` blocks.
- `JournalDao`/`ProjectDao`/`ProjectTaskDao` follow `TodoDao`'s exact shape
  (`observeFor...`/`listFor...` as `Flow`/`suspend` pairs, `upsert`/
  `upsertAll` via `OnConflictStrategy.REPLACE`, `deleteById`/`deleteByIds`,
  `clearAll` for `SessionClearer`'s logout wipe — **`SessionClearer` must be
  extended to clear all three new tables**, not just `TodoDao`, closing what
  would otherwise be a repeat of the cross-account-leak bug M11.8 already
  found and fixed for `todo`).
- `JournalDao` gains one query `JournalDao.findEntryDays(from, to): List<LocalDate>`
  (`SELECT DISTINCT day FROM journal_entry WHERE day BETWEEN :from AND :to ORDER BY day`)
  backing D5's client-side calendar markers — no network call.
- `ProjectListScreen`/`CategoryManagerScreen` call the generated
  `ProjectControllerApi`/`ProjectCategoryControllerApi` directly, no DAO
  (D10); `ProjectDetailScreen` and its three tabs read `ProjectDao`/
  `ProjectTaskDao` `Flow`s scoped to the open `projectId` (D9).

### 5.3 Writes

Same posture as M11 §6.4: every write (journal create/patch/delete; project/
category/task create/patch/delete/reorder; dependency create/delete) calls the
generated client directly; on success the response's row is immediately
upserted into the relevant DAO (no waiting for the next sync tick); on
failure (including "no network") the screen surfaces a plain error, no retry
queue. `DependencySection`'s create call surfaces the backend's `400`/`409`
body (self/cross-project/cycle/duplicate, M5 D3/D4) as an inline message —
same thing the web `TaskDependencySection` already does.

## 8. Open questions / risks

| # | Question | Notes |
| --- | --- | --- |
| Q1 | Is a hand-drawn Compose `Canvas` Gantt (D2) actually going to look acceptable at small phone widths, or does it need a horizontally-scrollable container from day one? | Build the scroll container in from the start rather than retrofitting it — a project with more than a handful of weeks' span will overflow a phone screen immediately, unlike the diamond/arrow rendering logic itself which is low-risk. |

## 10. Corrections found during implementation

- **Backend defect found and fixed, not purely Android-side as §4 assumed.**
  `TodoDtos.ReorderRequest`, `ProjectDtos.ReorderRequest`,
  `ProjectCategoryDtos.ReorderRequest`, and `ProjectTaskDtos.ReorderRequest`
  were four distinct Java records sharing one simple class name. springdoc
  names OpenAPI component schemas by simple class name alone, so the spec
  had exactly one `ReorderRequest` schema — whichever of the four it
  processed last (the `todo` one, carrying a required `day` field neither
  the project/category/task reorder endpoints take, and silently missing
  `ProjectTaskDtos`'s own `parentTaskId`). Every non-todo `:reorder` call
  the generated Android client would have made was therefore wrong. Fixed
  by renaming the three project-module records to
  `ReorderProjectsRequest`/`ReorderCategoriesRequest`/`ReorderTasksRequest`
  (`ProjectDtos`/`ProjectCategoryDtos`/`ProjectTaskDtos` plus their
  controllers) and regenerating the Kotlin client. Each now gets its own
  correctly-shaped request type. No wire-format change for any *existing*
  caller — the three were effectively broken for a generated client either
  way, and the web app's hand-written `fetch` calls never relied on the
  OpenAPI schema name.
- **`ProjectTaskResponse.toEntity()` needs `projectName`/`projectColor`
  passed in explicitly.** Unlike `ProjectTaskView` (the sync/list shape,
  which denormalizes both), a single-task write response
  (`ProjectTaskResponse`) carries neither — the caller already has both
  from the project it's editing a task within, so `ProjectTaskMappers.kt`'s
  second `toEntity` overload takes them as parameters rather than assuming
  they're present.
- **Room DAO tests, ViewModel `Turbine` tests, and Compose UI tests (§6)
  were not built**, despite being in this plan's own test table — mirroring
  what M11 *actually* shipped (a `SyncRepositoryTest` against mocked DAOs,
  nothing Room-instance-backed, no `TodoViewModelTest`) rather than what
  M11's own plan document described. Adding `androidx.room:room-testing` +
  an in-memory Room DB, and a Turbine dependency, would be new test
  infrastructure this milestone didn't otherwise need to introduce; revisit
  if a regression in the reorder-splice or sync fan-out logic actually
  surfaces.
- **The ViewModel split landed as four files, not the plan's three**
  (`ProjectViewModel`/`ProjectDetailViewModel`/`ProjectTaskViewModel`) — a
  fourth, `ProjectFormViewModel`, backs `ProjectFormScreen` (create/edit)
  separately from the list screen's own `ProjectViewModel`, the same
  "one screen, one ViewModel" precedent `JournalEntryViewModel` already set
  relative to `JournalViewModel`.
- **Category reordering got the same tap-based "Move up/down" treatment as
  task reordering (D4)**, even though D4's own text only committed to
  that for tasks — `CategoryManagerDialog` wires `POST
  /project-categories:reorder` to the same affordance rather than leaving it
  unimplemented, for consistency within the one milestone that touches both.
- **The Gantt tab's `onClick` (tap a row to open `TaskEditScreen`)** is
  row-based, not bar-hit-tested — tapping anywhere in a task's row opens
  that task's edit screen, rather than requiring a precise tap on the
  drawn bar/diamond. Simpler and, on a phone-sized target, more usable.
- **Found post-deploy: the widened `/sync` types silently orphaned
  pre-existing data on any device that already had M11's `todo`-only app
  installed.** `SyncCursorStore`'s single `since` cursor is shared across
  whatever `types` the app happens to request; an M11 device's cursor had
  already advanced (from its own `todo`-only syncs) by the time it updated
  to this milestone's build, so the very first post-update sync asked the
  backend for `journal`/`project`/`projectTask` rows *changed after* a
  cursor that predated nearly all of them — `changedSince` returns nothing
  for a row that hasn't been touched since before it, so those rows were
  never going to sync down on their own. Confirmed live: a project with 4
  tasks showed up (the project list screen is a live fetch, D10) with an
  empty task list (Room-backed, D9) on a phone that had M11 installed since
  before this update. Fixed in `SyncCursorStore` (a second key,
  `synced_types`, tracking which types this device has ever fully synced)
  and `SyncRepository` (if the fixed `REQUESTED_TYPES` set contains one not
  yet in `synced_types`, that one call ignores the stored cursor and syncs
  from `since=null`, then records the full set as synced) — covered by
  `SyncRepositoryTest`. The same mechanism will catch any *future*
  milestone's own widening for free, not just this one instance. The one
  device already caught by this had its stale cursor file cleared by hand
  (`adb run-as … rm files/datastore/kairon_sync.preferences_pb`) as an
  immediate workaround before the code fix landed; every other
  already-installed M11 device self-heals via this fix on its next launch
  after updating, no manual intervention needed.
