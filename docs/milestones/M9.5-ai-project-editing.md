# M9.5 — AI project editing from a description — implementation plan

Status: **Accepted — implemented.** Companion to [`../ROADMAP.md`](../ROADMAP.md) (M9.5 acceptance
criteria), [`../DESIGN.md`](../DESIGN.md) §13, [`../DATA_MODEL.md`](../DATA_MODEL.md),
and [`../adr/0002-ai-assistant-anthropic.md`](../adr/0002-ai-assistant-anthropic.md)
(this milestone adds a fifth assistant feature under that same ADR — it doesn't
revisit its decisions). Builds directly on the `assistant` module M8 established
and reuses M8.5's own precedents (string-keyed cross-referencing, cascade
exclusion, drop-and-log tolerance for bad model output) wherever the shape
matches; see D1 below for exactly what carries over.

Slotted as **M9.5** — between the already-implemented M9 and the still-unstarted
M10 — rather than renumbering, the same way M8.5 was slotted between M8 and M9.
`ROADMAP.md`'s M10/M11+ numbers, and every doc that already cites them, stay put.

## 1. Scope

### In

- A fifth assistant feature: given an **existing** project and a free-text
  description of the change the user wants ("add a punch-list task after
  inspection", "drop the old plumbing task", "this is now a Renovation
  project, not Home"), the LLM proposes a **diff** against that project's
  current state — tasks to add/update/remove, sibling reorderings,
  dependency edges to add/remove, and project-level field changes (name,
  description, size, dates, category) — for the user to review and apply in
  one action.
- `PROJECT_EDIT` added to `assistant_run.kind` (new migration, widening the
  check constraint again — same move as M8.5 D1).
- New table `assistant_suggested_project_edit`: one row per run, scoped to
  the target `project_id`, the whole proposed diff stored as `jsonb`,
  `PROPOSED → ACCEPTED | DISMISSED`.
- Three new read-side `ProjectsApi` port methods (`requireProject`,
  `tasksForProject`, `dependenciesForProject`) so the assistant module can
  build "here's the project as it stands today" context without depending on
  `projects.domain`/`projects.repo` — same reasoning as M8.5's `categories()`
  addition.
- One new write-side `ProjectsApi.applyProjectEdit` port method: one
  transactional call that applies an accepted diff — project field changes,
  task add/update/remove, sibling reordering, dependency add/remove —
  reusing `ProjectService`/`ProjectTaskService`/`TaskDependencyService`/
  `ProjectCategoryService` as internal collaborators, exactly like M8.5 D3
  did for whole-project creation.
- `POST /assistant/project-edits` (body: `projectId`, `description`;
  synchronous, like M8.5's project-plan call), `POST
  /assistant/suggested-project-edits/{id}:accept` (body:
  `excludedOperationKeys`), `POST
  /assistant/suggested-project-edits/{id}:dismiss`.
- Web: an "Edit with AI" button on `ProjectDetailPage`, a form (free-text
  description of the desired change), and a **diff review** screen grouped
  by change type (project fields, tasks added/updated/removed, dependencies
  added/removed, reordering) with per-change exclude checkboxes, mirroring
  M8.5's review screen but for a diff against existing data instead of a
  brand-new tree.
- A fifth per-feature opt-in, `assistant.projectEditing.enabled`, alongside
  the other four on `AccountPage`'s Assistant section.

### Out (deferred, with what would pick it up)

- **Field-level partial updates within one task/project change.** An
  `UPDATE` operation always carries that task's (or the project's) *complete*
  new field set, not a sparse per-field patch (D3) — same "whole-form
  overwrite" convention the existing manual PATCH endpoints already use, so
  there's no null-means-"unchanged"-vs-null-means-"clear it" ambiguity to
  resolve in a structured-output schema.
- **Task status, color, actual hours/dates, progress.** The model still never
  touches these (D5) — same posture M8.5 D10 took for `color`/`status` on
  creation, extended here to the handful of fields that only make sense as a
  record of what actually happened, not a plan. Marking something done stays
  a manual action (the task card, the board, or a linked todo's completion).
- **Optimistic-locking / concurrent-edit reconciliation.** If a task the diff
  references was deleted or changed between propose and accept, the
  operation touching it is dropped and logged (D8), not retried or
  conflict-surfaced — same tolerant posture as M8.5 D7's dependency handling,
  not a new concurrency-control mechanism.
- **Multi-turn refinement ("no, keep that task but change its date").** One
  description in, one diff out, review, apply or dismiss — the same
  single-shot loop M8.5 uses for generation. A tighter conversational
  iteration loop is a possible future enhancement once usage shows
  single-shot isn't enough.
- **Editing more than one project in a single request.** The diff always
  targets exactly one `projectId`, chosen by opening this dialog from that
  project's own detail page.

## 2. Decisions locked for this milestone

| # | Decision | Rationale |
| --- | --- | --- |
| D1 | **Reuse M8.5's cross-referencing and tolerance precedents wherever they apply**: a short LLM-chosen string `key` names a task the diff is *adding* (so other new tasks/dependencies/reorderings in the same diff can refer to it before it has a real id); a plain string field is instead parsed as a real `UUID` and matched against the project's current tasks when the diff refers to an *existing* task. Excluding an `ADD` operation at review time cascades to anything else in the same diff that refers to its key (M8.5 D6, generalized from "task+its children" to "any operation referencing this key"). A dependency or reorder entry naming an unknown/excluded/deleted-meanwhile reference is **dropped and logged at `warn`**, never failing the whole apply (M8.5 D7). | No reason to re-derive infrastructure and judgment calls M8.5 already made and that generalize cleanly — the only genuinely new decisions this milestone makes are D2–D11. |
| D2 | **The diff is an explicit operation list, not a full-state echo.** The model emits only the operations that represent an actual change: `taskOperations` (`ADD` \| `UPDATE` \| `REMOVE`), `dependencyOperations` (`ADD` \| `REMOVE`), `reorderOperations` (a full sibling order for one parent group — see D6), and an optional `projectChanges` block, present only if the project's own fields are changing. A task/dependency/the project itself that isn't mentioned at all is left completely untouched. | Keeps the prompt/response small (no need to re-emit every unchanged task just to prove it's unchanged) and avoids the "model retypes an unchanged date slightly wrong" risk a full-state echo would invite — every emitted operation is a real, reviewable change, which is also exactly what a diff-review UI wants to show. |
| D3 | **An `UPDATE` task operation (and a present `projectChanges` block) always carries the *complete* new field set for the thing it touches** — including fields the user didn't ask to change, copied forward from the current state the model was given in context — not a sparse per-field patch. | Resolves the null-ambiguity problem a structured-output schema can't express cleanly ("field omitted" and "field explicitly cleared" both serialize the same way), by reusing the exact convention `ProjectTaskService.patch`/`ProjectService.patch` already use for manual edits (their own doc comments call this "whole-form overwrite"): the model behaves like a user resubmitting the whole edit form, not a user describing a JSON Patch. The context given to the model (§4.4) always includes the full current field set for every task/the project itself, so "copy forward what you're not changing" is always possible. |
| D4 | **Dependency edges have no `UPDATE`** — changing a dependency's type or lag is a `REMOVE` of the old edge plus an `ADD` of the new one. | Matches `TaskDependencyService`'s own existing capability exactly — it has `create`/`delete`, no `patch`, so there is no dependency-update code path to reuse even if the schema offered one. |
| D5 | **The model never touches task `status`, `color`/`progressPercent`, `actualHours`, `actualStart`/`actualEnd`, or project `color`/`status`.** Scheduling/structural fields only: task `name`/`description`/`isMilestone`/`plannedStart`/`plannedEnd`/`estimateHours`/parent; project `name`/`description`/`size`/`startDate`/`endDate`/category. *(User decision — "structure + category", not "everything".)* | Confirmed with the user. Same posture as M8.5 D10: fields that record what actually happened, or pure workflow/presentation state, stay a manual action — a plan-editing feature proposing changes shouldn't also be the thing that marks work done or recolors a project. |
| D6 | **Sibling reordering is a dedicated `reorderOperations` list**, each entry a `{parentRef, orderedRefs}` pair — a full new order for one parent's children (or the top-level group, `parentRef == null`) — passed straight through to the existing `ProjectTaskService.reorder(userId, projectId, parentTaskId, orderedIds)` as an ordinary same-package collaborator call, no new `ProjectsApi` port method needed. | `reorder` already requires *exactly* the current sibling group's full membership, by id (`ProjectTaskService.reorder`'s own validation) — reusing it as-is means a reorder request can't accidentally drop or duplicate a sibling; `ProjectEditApplyService` lives in the same `projects.app` package as `ProjectTaskService`, so this needs no port surface at all, unlike the cross-module `ADD`/`UPDATE`/`REMOVE`/dependency operations. |
| D7 | **A single new per-feature opt-in**, `assistant.projectEditing.enabled` (default `false`), alongside the other four in `app_user.preferences.assistant`. *(User decision — a separate toggle from project generation.)* | `DESIGN.md` §13.5: "opt-in is per feature." Confirmed with the user: generating a brand-new project and rewriting parts of an existing one carry different risk profiles (the latter can delete/reshape a user's existing data), so a user opted into one shouldn't be silently opted into the other. |
| D8 | **Review is per-operation include/exclude, applied atomically** — nothing is written until the user clicks Apply, and Apply either applies the whole accepted subset in one transaction or fails entirely (no partial apply visible to the user, beyond the already-established drop-and-log tolerance for stale/invalid references at D1). *(User decision.)* | Confirmed with the user, and required by `DESIGN.md` §13.4's "suggest-only — accepting a suggestion is always an explicit user action" — this is the one principle every existing assistant feature in this codebase upholds, and an edit feature that can delete existing tasks needs it more than any of them. |
| D9 | **`kairon.assistant.project-edit.max-operations`** (default 60) caps the *total* operation count (`taskOperations` + `dependencyOperations` + `reorderOperations` entries, each reorder entry counted by its `orderedRefs` size) after the response comes back — same enforcement style and same reasoning as M8.5 D7's `max-tasks`, just counting operations instead of tasks since this payload's size isn't just "how many tasks." | Bounds prompt/response cost and review-screen size for a runaway description against a very large project. |
| D10 | **Authorization/error shape matches every other `assistant` endpoint, plus one extra check**: `POST /assistant/project-edits` 404s immediately (before any run row is even created) if `projectId` doesn't resolve for the caller via the new `ProjectsApi.requireProject`; `assistant_suggested_project_edit` rows scoped `WHERE id = ? AND user_id = ?` (404 on missing/foreign); `409` if `:accept`/`:dismiss` is called on a row that isn't `PROPOSED`; `403` for disabled/opted-out/budget-exceeded; `502`/`503` for upstream failures. | Consistency with M8/M8.5's existing controllers, plus the one genuinely new failure mode this feature has that generation didn't: the target project itself can be missing/foreign/deleted, which should fail fast rather than waste a run. |
| D11 | **Everything else is reused unchanged from M8/M8.5**: the same `AnthropicClient` bean and circuit breaker, the same per-user monthly token budget pre-flight check (same pool, no separate budget), the same `/assistant/**` Bucket4j rate limiter (with this feature's new path added to `kairon.assistant.rate-limit.paths`, per M8.5's own "corrections found during implementation" note that the pattern isn't actually a wildcard), the same 502/503 upstream-failure mapping, and the same **synchronous** run (a diff against a project capped at `max-operations` is still one structured-output call). | No reason to re-derive infrastructure M8/M8.5 already built generically. |

New migration (next available version — confirm the exact number against
`backend/src/main/resources/db/migration/` at implementation time; `V009` is

CREATE TABLE assistant_suggested_project_edit (
    id          UUID PRIMARY KEY,
    run_id      UUID NOT NULL REFERENCES assistant_run(id) ON DELETE CASCADE,
    user_id     UUID NOT NULL REFERENCES app_user(id),
    project_id  UUID NOT NULL REFERENCES project(id) ON DELETE CASCADE,

    created_at  TIMESTAMPTZ NOT NULL,
    updated_at  TIMESTAMPTZ NOT NULL,

);
CREATE UNIQUE INDEX idx_assistant_suggested_project_edit_run ON assistant_suggested_project_edit(run_id);

    ON assistant_suggested_project_edit(project_id);

## 4. Backend

### 4.1 New `ProjectsApi` port methods

```java
/** Resolves a project the caller owns; 404 if missing, foreign, or soft-deleted. */
ProjectView requireProject(UserId userId, UUID projectId);

/** All non-deleted tasks of a project the caller owns; 404 if the project itself isn't visible. */
List<ProjectTaskView> tasksForProject(UserId userId, UUID projectId);

/** All dependency edges of a project the caller owns; 404 if the project itself isn't visible. */

/**
 * Applies an accepted edit diff to an existing project in one transaction —
 * project field changes, task add/update/remove, sibling reordering, and
 * dependency add/remove. Unresolvable/stale references are dropped and
 * logged, never failing the whole apply (D1/D8).
 */
ProjectView applyProjectEdit(UserId userId, UUID projectId, ProjectEditCommand command);
```

New `projects.api` records:

```java
public record ProjectEditCommand(
        ProjectFieldChanges projectChanges,              // nullable
        List<TaskOperation> taskOperations,
        List<DependencyOperation> dependencyOperations,
        List<ReorderOperation> reorderOperations) {
}

public record ProjectFieldChanges(
        String name, String description, String size, LocalDate startDate, LocalDate endDate,
        UUID categoryId, String newCategoryName) {           // same mutually-exclusive pair as ProjectPlanCommand
}

        String op,                                        // ADD | UPDATE | REMOVE
        UUID existingTaskId,                              // UPDATE/REMOVE; null for ADD
        String key,                                        // ADD only, for same-diff cross-references
        String parentRef,                                  // existing task id (as string) or a same-diff key; null = top-level
        String name, String description, boolean isMilestone,
        LocalDate plannedStart, LocalDate plannedEnd, BigDecimal estimateHours) {
}

public record DependencyOperation(
        String op,                                        // ADD | REMOVE
        UUID existingDependencyId,                         // REMOVE only
        String predecessorRef, String successorRef,        // ADD only; existing task id or same-diff key
        String type, Integer lagDays) {
}

public record ReorderOperation(String parentRef, List<String> orderedRefs) {  // existing task ids or same-diff keys
}
```

### 4.2 `projects.app.ProjectEditApplyService` (`@Service`, package-private)

Same shape as M8.5's `ProjectPlanImportService`, applying in a fixed order
inside one `@Transactional` method so later steps can see earlier ones' new
ids:

1. `projectChanges`, if present → `ProjectService.patch` (category resolved
   via the same create-or-match-by-name helper `ProjectPlanImportService`
   already has — extracted into a small shared `CategoryResolver` the two
   services both call, rather than duplicated).
2. `REMOVE` task operations → `ProjectTaskService.delete` (already cascades
   to subtasks and dependency edges).
3. `ADD` task operations, parent-before-child within the new set →
   `ProjectTaskService.create`, building a `key → UUID` map exactly like
   `ProjectPlanImportService` does.
4. `UPDATE` task operations → `ProjectTaskService.patch`, resolving
   `parentRef` against either a real existing id or the `key → UUID` map.
5. `reorderOperations` → `ProjectTaskService.reorder` directly (D6 — no port
   method, same-package call).
6. `REMOVE` dependency operations → `TaskDependencyService.delete`.
7. `ADD` dependency operations → `TaskDependencyService.create`, resolving
   `predecessorRef`/`successorRef` the same way; drop-and-log on an unknown
   reference or a rejection (cycle/duplicate), exactly like M8.5 D7.
8. Return `projectService.get(userId, projectId)`.

A reference string is resolved "existing-id-first": try `UUID.fromString`
and look it up among the project's current (or just-created) tasks; if that
fails or doesn't match, treat it as a same-diff `key`. LLM-chosen keys are
short (`"n1"`), so a collision with a real UUID's string form is not a
practical concern.

### 4.4 `ProjectEditContextBuilder` (new, `assistant.app`)

Fetches, via the new `ProjectsApi` methods, the target project
(`requireProject` — 404s here if it's not the caller's), its current tasks
(`tasksForProject`), its current dependency edges (`dependenciesForProject`),
and the user's categories (`categories`, reused from M8.5). Renders all of it
into the user content as the "current state" the model edits against —
task ids included verbatim so the model can reference them in
`existingTaskId`/`*Ref` fields — followed by the user's free-text
description of the desired change.

**System prompt** (constant, cacheable):

```
You are Kairon's project-editing assistant. You're given a project's current
state — its fields, its task tree, and its dependency edges, each with its
real id — plus a free-text description of a change the user wants. Propose a
diff: only the operations that represent an actual change.

Rules:
- Only emit an operation for something that is actually changing. Don't
  restate tasks, dependencies, or project fields that aren't affected.
- An UPDATE operation must carry that task's complete new field set,
  including fields copied forward unchanged from its current state — never a
  partial patch.
- Reference an existing task by the real id shown in its current state.
  Reference a task you're adding in this same response by a short key you
  choose (e.g. "n1") — never invent an id for something that doesn't exist
  yet.
- At most one level of nesting, same as the project's own existing tasks.
- A milestone is a zero-duration marker (plannedStart == plannedEnd).
- To change a dependency's type or lag, remove the old edge and add the new
  one — there's no update for a dependency.
- Only reorder a sibling group the user's description actually implies
  reordering for.
- Suggest a project categoryName the same way project generation does: match
  an existing category by name if one clearly fits, propose a short new one
  otherwise, or omit it entirely if the category isn't changing.
```

Same caching reasoning as M8/M8.5: the system prompt carries no per-request
data, so its cacheable prefix never invalidates.

### 4.5 `AssistantRunService.requestProjectEdit`

```java
@Transactional
public AssistantRunView requestProjectEdit(UserId userId, UUID projectId, String description) {
    AssistantPreferencesView prefs = requireProjectEditingAvailable(userId); // D7/D10
    projectsApi.requireProject(userId, projectId); // 404 fast, before any run row (D10)
    requireWithinBudget(userId);

    String model = resolveModel(prefs);
    AssistantRun run = AssistantRun.pending(userId.value(), AssistantRunKind.PROJECT_EDIT, null, null, model);
    runs.save(run);

    ProjectEditContextBuilder.Context context = projectEditContextBuilder.build(userId, projectId, description);
    run.start(context.inputSnapshot());
    runs.save(run);

    try {
        AnthropicClient.ProjectEditResult result = anthropicClient.generateProjectEdit(
                new AnthropicClient.ProjectEditRequest(context.systemPrompt(), context.userContent(), model));

        AssistantSuggestedProjectEdit saved = saveSuggestedEdit(run, projectId, result.diff(), context.categories());
        run.succeed(result.inputTokens(), result.outputTokens());
        runs.save(run);
        return AssistantMapper.toRunView(run, List.of(), null, toEditView(saved));
    } catch (AssistantUpstreamException e) {
        run.fail(e.sanitizedDetail());
        runs.save(run);
        throw e.toApiException();
    }
}
```

`periodStart`/`periodEnd` are left `null` — this run kind has no natural
period (the column is nullable; confirmed against `V007`). `max-operations`
capping (D9) happens in `saveSuggestedEdit`, same style as M8.5's
`saveSuggestedProject`.

### 4.6 `SuggestedProjectEditService` (new, `assistant.app`)

```java
@Transactional
public ProjectView accept(UserId userId, UUID id, List<String> excludedOperationKeys) {
    AssistantSuggestedProjectEdit row = require(userId, id);          // 404
    requireProposed(row);                                              // 409 otherwise
    PersistedProjectEdit diff = parse(row);
    Set<String> excluded = cascadeExclude(diff, excludedOperationKeys); // D1, generalized
    ProjectEditCommand command = toCommand(diff, excluded);
    ProjectView updated = projectsApi.applyProjectEdit(userId, row.getProjectId(), command);
    row.accept();
    log.info("Accepted project edit {} userId={} projectId={}", id, userId.value(), row.getProjectId());
    return updated;
}

@Transactional
public AssistantSuggestedProjectEditView dismiss(UserId userId, UUID id) { /* same shape as M8.5 */ }
```

The review-time exclusion key for one operation is positional —
`"task:<index>"`/`"dependency:<index>"`/`"project"` — but `cascadeExclude`
still reasons about the underlying semantic key (an excluded `ADD`'s `key`
field) when deciding what else to drop, the same two-level scheme M8.5 D6
used (positional checkbox, semantic cascade).

## 11. Corrections found during implementation

- **D3's "the model echoes unchanged fields" convention needed a code-side
  backstop.** Nothing actually enforces that the model's `projectChanges`
  carries every field — a partial block (e.g. only `categoryName` set,
  everything else `null`) hit `ProjectService.patch`'s "name must not be
  blank" validation, since that method is itself a whole-form overwrite with
  no concept of "leave unchanged." Fixed in `ProjectEditApplyService.applyProjectChanges`:
  fetch the project's current state and fall back to its current value for
  any field the diff left `null`, before building the `PatchCommand` —
  the same tolerant-of-imperfect-model-output posture D1 already established
  for references, extended here to plain field values.
- **`ProjectTaskView` doesn't exist in a form `dependenciesForProject` could
  reuse directly.** `TaskDependencyView` (the dependency projection
  `TaskDependencyService` already returns) lives in `projects.app`, not
  `projects.api` — unreachable from the assistant module under the
  ArchUnit module-boundary rule. Added `ProjectsApi.DependencyEdge`, a thin
  nested record mirroring `ProjectCategorySummary`'s own precedent, as the
  cross-module equivalent; `ProjectTaskService.dependenciesForProject` maps
  `TaskDependencyService.list`'s result down to it.
- **`ProjectTaskService`'s existing private `requireProject(UserId, UUID)`
  helper collided with the new `ProjectsApi.requireProject` port method of
  the same name** (same erasure, different return type — not a valid
  overload). Renamed the private helper to `requireOwnedProject` rather than
  the port method, since the port method's name is part of the public
  contract other modules now call by that name.
- **The shared category-resolution logic needed extracting before it could
  be reused, not after.** As planned (§4.2), `ProjectPlanImportService`'s
  `resolveCategory` was pulled out into a new `CategoryResolver` component
  both it and `ProjectEditApplyService` now depend on; `ProjectPlanImportServiceTest`
  needed a one-line update (constructing `new CategoryResolver(categoryService)`
  instead of passing the mocked `ProjectCategoryService` straight through) —
  the mock itself still works transparently since `CategoryResolver` is a
  thin, concrete (not interface) wrapper.
- **Dependency "ops have no UPDATE" (D4) and task reference resolution
  needed one shared rule, not two.** Rather than separate resolution paths
  for "an existing id" vs. "a same-diff key," every `*Ref`/`existingTaskId`/
  `existingDependencyId` string is resolved the same way everywhere
  (`ProjectEditApplyService.resolveRef`, `SuggestedProjectEditService`'s
  own id-parsing): try `UUID.fromString` first, fall back to the same-command
  `key` map. One rule, reused by both the accept-time cascade logic and the
  apply-time mutation logic, rather than two slightly different ones.
