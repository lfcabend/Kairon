# M10.5 — MCP server for assistant features (bring-your-own Claude subscription) — implementation plan

Status: **Accepted — implemented.** Companion to [`../ROADMAP.md`](../ROADMAP.md) (M10.5's sketch —
this plan locks the decisions that sketch left open),
[`../adr/0002-ai-assistant-anthropic.md`](../adr/0002-ai-assistant-anthropic.md)
(this milestone is a real, deliberate amendment to that ADR's "all calls are
server-side" and "a single `ANTHROPIC_API_KEY`… serves all users" framing —
see §10), and [`../DATA_MODEL.md`](../DATA_MODEL.md).

Today every assistant feature is paid for per-token against one
instance-wide `ANTHROPIC_API_KEY`. This milestone adds a second,
zero-marginal-cost entry point: a standalone **MCP server**, run locally by
the user under their own Claude subscription (via Claude Code), that reads
Kairon's assistant context and writes results back into the exact same
`assistant_run`/`assistant_suggested_*` rows the paid API path writes today —
so a Claude-Code-authored suggestion shows up in the normal web/Android
review UI unchanged. The existing Anthropic-API path is untouched and stays
the only path for the scheduled summary sweep (M10) and for any user without
Claude Code.

Several foundational questions the original sketch left open are now
settled (user decisions, this conversation):

1. **Process boundary**: a standalone process, not in-process in `assistant`.
2. **Auth**: a new long-lived personal access token (PAT), not the existing
   refresh-token mechanism.
3. **Review step**: a write-back tool always creates a `PROPOSED` row —
   never a direct accept. ADR-0002's "suggest-only, the user stays in
   control" stance is **unchanged**, including for this new entry point.
4. **Scope**: the five assistant context/write-back pairs **plus** general
   read-only tools over `todo`/`journal`/`projects` for ad hoc queries.
5. **Stack**: TypeScript/Node.js, a new top-level `mcp-server/` directory —
   not a Gradle subproject. It never touches the Anthropic SDK, so the
   ArchUnit rule confining that import to `assistant` stays meaningful and
   unaffected.
6. **Token budget**: an MCP-submitted run does **not** draw from the
   per-user monthly Anthropic token budget — zero real spend occurred.
7. **General reads**: the MCP server calls Kairon's **existing** REST
   endpoints (`GET /todo`, `GET /journal`, `GET /projects/**`, …) — no new
   backend read surface for those.

**Revised after first draft (same conversation): this is a remotely-reachable,
always-on, multi-tenant deployment, not a locally stdio-launched subprocess.**
The user wants to drive it from Claude Code on their phone, which means the
server can't be something Claude Code spawns and owns the lifetime of on the
local machine it's running on — it has to already be running, reachable over
the network, when the phone connects. This reshapes §1/§6/§7/§9/§11 below
(the backend API surface — §2–§5 — is **unaffected**, since the MCP server
was always going to be a REST client of it regardless of transport):

8. **Transport**: MCP's Streamable HTTP transport (not stdio) — the server
   is a small always-running HTTP service.
9. **Multi-tenancy/auth**: the server holds **no credential of its own**.
   Every request must carry `Authorization: Bearer <PAT>`; that exact value
   is forwarded verbatim to Kairon's backend for every call made while
   handling that request — no session-to-user caching, nothing stored
   server-side between requests. *(This follows necessarily from "shared,
   always-on, reachable from any of the user's devices" — not a separate
   open question.)*
10. **Deployment**: Dockerized, deployed to the **same k8s namespace** as
    the rest of Kairon, as its **own separate Helm chart/release** (not a
    new conditional piece of the existing `kairon` chart). *(User decision.)*
11. **Reachability**: a new top-level ingress path (`/mcp`) on the
    **same** xbmc Tailscale Funnel hostname the web app already uses —
    same TLS termination, same "public but obscure HTTPS URL, login-gated"
    security posture the rest of the app already has. *(User decision.)*

## 1. Scope

### In

- A new top-level `mcp-server/` directory (TypeScript, Node.js, the official
  `@modelcontextprotocol/sdk`, Streamable HTTP transport) — a thin,
  stateless REST client over Kairon's existing and newly-added API, always
  running, reachable from any of the user's devices (including Claude Code
  on their phone).
- **Dockerized and deployed**: a new `docker/mcp-server.Dockerfile`, a new
  GHCR image, and a new, separate Helm chart (`deploy/helm/kairon-mcp/`)
  deployed to the **same namespace** as the main `kairon` release — its own
  Deployment/Service/Ingress, reachable at a new top-level path on the
  existing xbmc Tailscale Funnel hostname (decisions 8–11 above).
- **Personal access tokens (PATs)**: a new `identity`-owned mechanism for a
  user to mint a long-lived, named, individually revocable credential
  distinct from the 15-minute web/Android JWT — generated and managed from
  the web Account page, pasted into the MCP server's local config.
- A new, narrow **PAT auth scope**: read-only on `todo`/`journal`/`projects`
  (reusing existing endpoints verbatim) plus ten new `assistant` endpoints
  (below). Nothing else — no account mutation, no direct todo/journal/
  project writes, no access to the *existing* accept/dismiss/assistant
  endpoints. A normal JWT keeps unrestricted access exactly as today.
- **Ten new endpoints** under `/api/v1/assistant/mcp/**`, splitting each of
  the five existing assistant features' "request + dispatch" shape into a
  context-read half (no `assistant_run` row created) and a write-back half
  (creates the same `assistant_run`/`assistant_suggested_*` rows the
  Anthropic-API path creates, immediately `SUCCEEDED`, tagged with a new
  `source = MCP` column).
- `mcp-server/` tool surface: five `get_*_context` / `submit_*` pairs
  mirroring those ten endpoints, plus general read-only tools over
  `todo`/`journal`/`projects`.
- Web: a "Developer access" section on the Account page — generate (shown
  once), list, revoke PATs; a small "via MCP" badge on assistant run history
  rows (the existing Summaries screen and the suggestion review screens both
  already render `AssistantRunView`, which gains a `source` field).
- Reuses, unchanged, M8–M10's existing per-feature opt-in flags, suggestion
  capping, category resolution, model-override validation, and (for
  summaries) the server-computed, never-model-authored stats table.
- Tests: backend (PAT lifecycle, the new security wiring, the ten new
  endpoints, an `@SpringBootTest` end-to-end flow), `mcp-server` (Vitest,
  mocked HTTP), web (the new Account section).

### Out (deferred, with what would pick it up)

- **A direct-accept write-back variant** — considered and declined (user
  decision, D4 below). ADR-0002's suggest-only invariant stays absolute
  regardless of entry point. Revisit only as a deliberate, explicit future
  amendment, not a quiet addition to this milestone.
- **Bring-your-own Anthropic API key per user** — a different backlog item
  (`ROADMAP.md`'s own backlog list); unrelated to this milestone, which adds
  a *second* entry point, not a second billing model for the first one.
- **Android MCP access / PAT management UI** — PATs are managed from web
  only this milestone; `AssistantRunView.source` is available to Android for
  free once the generated client regenerates, but no Android screen change
  is scoped here.
- **New, LLM-shaped read endpoints for the general-read tools** — settled
  (decision 7 above): reuse the existing REST surface as-is.
- **Structured (JSON) context payloads distinct from the rendered prompt
  string** — see D12: the five `get_*_context` tools return the *same*
  `{systemPrompt, userContent}` shape each `*ContextBuilder` already
  renders, not a parallel structured-data representation. A genuine,
  deliberate narrowing of the original `ROADMAP.md` wording — called out
  explicitly, not silently reinterpreted (see D12's rationale and open
  question Q1).
- **Rate-limiting tuned specifically for PAT traffic at the backend layer**
  — the ten new endpoints join the existing `/assistant/**` rate limiter's
  literal `paths` list (same budget, same mechanism); no new, PAT-specific
  backend limiter. (A coarse ingress-level limit on the new, publicly
  reachable `/mcp` path is in scope — see D-ingress below — but that's a
  one-line annotation, not new application code.)
- **A CI drift check or published artifact for `mcp-server/`'s source** — it
  has no generated code and no coupling to the backend's OpenAPI spec (it's
  a hand-written REST client, same posture as `web/`'s own hand-written
  `src/lib/api/*.ts`), so there's nothing to regenerate or diff. (Its
  *Docker image*, unlike its source, is built/scanned/pushed in CI like any
  other deployed image — that part is in scope, §6b.)
- **Full OAuth 2.1 for the remote MCP connection** — considered and declined
  in favor of a manually-configured bearer header (decision 9/D1-auth);
  revisit only if the real Claude Code remote-MCP client turns out to
  require OAuth discovery for an unlisted, self-hosted server (flagged as a
  real risk, not a settled non-issue — see Q7).
- **A values-local.yaml / kind-cluster overlay for the new chart** — xbmc is
  the only real target for this feature (reaching it from a phone requires
  the real Funnel hostname); a local-dev overlay can be added later if
  iterating against kind turns out to be worth it.

## 2. Decisions

| # | Decision | Rationale |
| --- | --- | --- |
| D1 | **Standalone process, TypeScript/Node.js, new top-level `mcp-server/` directory, Streamable HTTP transport (not stdio)** — not a Gradle subproject, not in-process in `assistant`. Always running, deployed to k8s (D-chart below), reachable from any of the user's devices. *(User decision, revised mid-conversation from an initially-sketched local-stdio-subprocess shape once "Claude Code on my phone" made clear the server has to already be running and network-reachable, not spawned by the client that connects to it.)* | Keeps the "only `assistant` imports the Anthropic SDK" ArchUnit rule meaningful (this process imports no Anthropic SDK of any kind — the reasoning happens inside the user's own Claude Code session, outside Kairon entirely) and lets it be deployed/versioned independently of the backend's release cycle. TypeScript because the official MCP SDK is most mature there and supports Streamable HTTP natively; Node has zero coupling to the Gradle/JVM toolchain, matching `web/`'s own separate npm toolchain precedent. |
| D1-auth | **The MCP server holds no credential of its own and keeps no per-connection state.** Every incoming HTTP request must carry `Authorization: Bearer <PAT>`; a request missing or failing that check is rejected (`401`) before any tool handler runs. The exact same token is forwarded verbatim as the `Authorization` header on every Kairon API call made while handling that one request — never cached, never associated with a session id across requests. *(Follows necessarily from decision 9 — a shared, always-on, multi-device service can't bake in one user's token the way a locally-launched, per-user subprocess could have.)* | This is what makes one deployment safely multi-tenant: two different users' phones (or two devices for the same user) hitting the same pod concurrently are isolated purely by which bearer token each request carries, with zero shared mutable state to leak between them. It also means a pod restart or horizontal replica loses nothing — there is nothing stateful to lose — and the backend's own `PersonalAccessTokenValidator` (D15) remains the *only* place a PAT is actually checked; the MCP server deliberately does no token validation of its own; an invalid/expired/revoked PAT simply surfaces as whatever `401`/`403` the backend already returns, propagated back as a tool error. |
| D1-chart | **A separate Helm chart, `deploy/helm/kairon-mcp/`, deployed to the same namespace as the `kairon` release as its own independent `helm upgrade`.** *(User decision over extending the existing chart with a conditional flag.)* | Keeps the MCP server's own release lifecycle (image tag, rollout, rollback) decoupled from the main app's — deploying or rolling back one never touches the other's `helm upgrade` history, at the cost of two release names to track in the same namespace instead of one. Communicates with the backend over the in-cluster Service DNS name (e.g. `http://kairon.kairon.svc.cluster.local:8080/kairon` — exact name confirmed against the existing chart's `service.yaml` at implementation time), not by round-tripping back out through the public Funnel URL. |
| D1-ingress | **A new `Ingress` object (owned by the new chart) for the same host the main app's ingress already serves (`xbmc.tail9ae0e9.ts.net`), at a new top-level path `/mcp`**, with `nginx.ingress.kubernetes.io/proxy-buffering: "off"` and a longer `proxy-read-timeout` (Streamable HTTP keeps its GET/SSE half open for the life of a session). *(User decision — a sibling path over a separate subdomain.)* | `ingress-nginx` merges multiple `Ingress` objects that target the same host into one effective configuration as long as their paths don't collide, so this needs **zero changes to the existing `kairon` chart's own `ingress.yaml`** — the new chart is additive at the ingress layer the same way it's additive everywhere else. No new DNS, no new cert — the Funnel/ingress already terminates TLS for this host. |
| D1-ci | **A new `docker/mcp-server.Dockerfile`** (Node multi-stage: install + `tsc` build, then a slim `node:lts-alpine` runtime stage, no JDK involved at all) **and a new GHCR image**, built/Trivy-scanned/pushed by `.github/workflows/deploy.yml` alongside the existing app/migrator images (same job, one more matrix leg or copy-pasted step — M14's own "streamline the near-duplicate Trivy steps" backlog item is the natural place to revisit the copy-paste, not this milestone). A second `helm upgrade` step targets the new chart, same xbmc `Environment`/Tailscale-connected runner the existing deploy step already uses. | Reuses every piece of M7's existing deploy pipeline (image scan, GHCR push, Tailscale-connected `helm upgrade` runner, the `xbmc` `Environment` gate) rather than inventing a second CI mechanism for what is, operationally, just one more image and one more release in the same pipeline. |
| D2 | **A new personal access token (PAT) mechanism**, not a reused refresh token. New `identity`-owned table `personal_access_token`, hashed (SHA-256, same as `RefreshTokenService.hash`) — the raw value is shown to the user exactly once at creation. *(User decision.)* | A refresh token is designed to rotate on every use and be family-revoked on reuse detection — using one as a static, long-lived credential fights that design head-on. A PAT is a deliberately different credential shape: long-lived until explicitly revoked, generated on demand from Settings, independent of any login session. |
| D3 | **PAT scope is fixed and narrow, enforced in `SecurityConfig`, not per-token.** A PAT may call: `GET` on `/api/v1/todo/**`, `/api/v1/journal/**`, `/api/v1/projects/**` (existing endpoints, read-only), and anything under `/api/v1/assistant/mcp/**` (the ten new endpoints, §4.4). Every other `/api/v1/**` path — including the *existing* `/assistant/**` endpoints, `PATCH /me`, every write on `todo`/`journal`/`projects` — requires the authority a PAT is never granted. A normal JWT is unaffected and keeps full access everywhere it does today. | There's exactly one scope needed for v1 (general reads + the five assistant pairs) — a per-token scope *selection* would be premature machinery for a single fixed capability set (`CLAUDE.md`'s "no premature abstraction" bias). Fixing the boundary in code, not data, also means it can't be loosened by a bug in token-issuance logic — only by a deliberate `SecurityConfig` change. |
| D4 | **A write-back tool always creates a `PROPOSED` suggestion row (or, for summary/reflection, a `SUCCEEDED` run with no accept/dismiss step of its own) — identical to what the Anthropic-API path creates today.** No direct-accept variant exists. *(User decision.)* | ADR-0002's "the assistant never writes a `todo_item`/`journal_entry`/`project`… the user accepts" stance is explicitly preserved, unmodified, for this new entry point — a wrong or hallucinated Claude-Code-authored suggestion never silently becomes real data just because it came from a trusted local session. The normal web/Android accept/dismiss screens are the only path to real data, regardless of which door the suggestion came in through. |
| D5 | **A write-back tool never draws from the per-user monthly Anthropic token budget** (`requireWithinBudget` is simply not called on this path). *(User decision.)* | The budget exists to cap the *instance owner's* Anthropic bill (ADR-0002) — an MCP write-back spends none of that money, so gating a zero-marginal-cost path behind a cost-motivated cap would block something free for a reason that doesn't apply to it. |
| D6 | **General read-only MCP tools call Kairon's existing REST endpoints** (`GET /todo`, `GET /journal`, `GET /projects/**`, …) rather than a new, LLM-shaped read surface. *(User decision.)* | Zero new backend code for this half of the scope; the `mcp-server` tool handlers are thin translators from an MCP tool call to the same call the web app already makes. Revisit only if real usage shows the existing DTOs are awkward for a tool call — not something to anticipate speculatively. |
| D7 | **Every per-feature opt-in flag still gates the MCP path exactly as it gates the API path** — `requireTodoSuggestionsAvailable`/`requireProjectGenerationAvailable`/etc. (existing) are reused unchanged for both the context-read and write-back half of each feature. | `ROADMAP.md`'s own M10.5 bullet: "No change to existing opt-in flags… purely additive." A PAT existing must never be a side-channel around a feature a user has deliberately left off. |
| D8 | **A context-read call creates no `assistant_run` row.** The row is created only at write-back time, once a result actually exists to persist — mirroring the fact that the real "call" (the LLM reasoning) happened entirely outside the instance, inside the user's own Claude Code session. | A context read with no following write-back leaves no audit row, which is a genuine, narrow departure from ADR-0002's "every interaction is a persisted `assistant_run`" framing — called out explicitly in §10's ADR update rather than silently left inconsistent with that document. The controller's own `log.debug` is the only trace of a context-only read, same visibility level as any other authenticated `GET`. |
| D9 | **Ten new endpoints under a new `/api/v1/assistant/mcp/**` prefix**, five `POST .../:context` (read, returns `{systemPrompt, userContent}` — a request *body* is needed for several of these, e.g. a project-edit's free-text description, so `GET` with a long query string is the wrong shape; kept consistent with this app's existing `resource:action` suffix convention, e.g. `todo:rollover-preview`) and five plain `POST` (write-back). Both groups accept a normal JWT too (a PAT is additionally restricted to only these paths — D3 — but nothing stops the web app itself from calling them later if ever useful). | Reuses the single existing convention for "a POST that isn't a plain resource create" already established by `planning/today:promote` and `todo:rollover-preview`, rather than inventing a new URL shape for this milestone specifically. |
| D10 | **`AssistantRun` gains a `source` column (`API` \| `MCP`, default `API`)** — purely descriptive/audit, read by `AssistantRunView`/the web run-history badge; no behavioral branch anywhere reads it except the (now-skipped, D5) budget check's absence. | The cheapest way to make "this suggestion came from your own Claude Code session, not the paid API" visible and auditable without inventing a second run table or a parallel history feed — matches `assistant_batch`'s own precedent (M10 D21) of adding one small, additive column/table rather than bending an existing column's meaning. |
| D11 | **A write-back's `model` field is free-text, caller-reported, and never validated against `AssistantRunService.KNOWN_MODELS`.** It's descriptive metadata only (audit: "which model actually produced this") — never passed to any Anthropic SDK call, since none happens on this path. Defaults to `"mcp"` if the tool call doesn't supply one. | `KNOWN_MODELS` exists to protect a real `sdk.messages().create(...)` call from an invalid model string; this path never makes that call, so the validation it protects against doesn't apply. Rejecting an unrecognized-but-honest model name (e.g. a future Claude model Kairon's own `KNOWN_MODELS` list hasn't caught up to yet) would be actively wrong here. |
| D12 | **The five `get_*_context` tools return the exact same `{systemPrompt, userContent}` string pair each `*ContextBuilder` already renders for the Anthropic API call — not a parallel structured-JSON representation.** A deliberate narrowing of `ROADMAP.md`'s original "as structured data instead of a rendered prompt string" wording, made while drafting this plan (flagged here, not silently substituted) — see Q1. | Building a second, JSON-shaped representation of the same five context sources, in parallel with the existing string-rendering builders, is real duplicated work for a benefit that doesn't obviously exist: an LLM reasons over well-formatted prose at least as well as over equivalent JSON, and every one of these builders already renders clearly labeled, structured-*looking* text (e.g. `ProjectEditContextBuilder`'s `"- id=... name=\"...\" start=... end=..."` task lines). Reusing the builders verbatim is zero new backend logic for this half of the feature; a real JSON shape is one to build later specifically if a user's own Claude Code session turns out to parse the prose worse than expected (Q1). |
| D13 | **`submit_summary` still appends the server-computed, never-model-authored stats table after the submitted narrative** — exactly like the existing Anthropic-API path (M9 D16) and the batch path (M10 D23). The write-back rebuilds `SummaryContextBuilder.Context` server-side (cheap, deterministic SQL, no LLM call) purely to call `.renderStatsTable()`, then stores `narrative + "\n\n" + statsTable` as `output_markdown`. `submit_journal_reflection` appends nothing, matching M10 D11 (a reflection has no stats table on *any* path). | The numbers in a summary must never be model-authored on *any* entry point, not just the Anthropic-API one — an MCP-submitted summary whose stats came from Claude's own (possibly wrong) arithmetic would quietly break the one invariant this feature exists to guarantee. Rebuilding the context is cheap (it's the same SQL aggregation `SummaryContextBuilder` already does, no network call) so there's no real cost to re-deriving it at write-back time rather than trusting a number the caller supplies. |
| D14 | **`submit_project_edit` re-runs `ProjectsApi.requireProject` before accepting the diff** (404 if `projectId` isn't the caller's own), and `submit_journal_reflection` re-runs the empty-week check (M10 D8) before accepting the narrative — both exactly as their existing request-time counterparts do. | A write-back tool is still an authenticated call from a long-lived credential, not a trusted continuation of a request this server itself issued — every authorization/precondition check the synchronous path makes up front, the write-back path re-makes up front too, rather than assuming the caller only ever calls it in the "correct" sequence. |
| D15 | **A new SPI interface, `common.security.PersonalAccessTokenValidator`, is the only way `common` knows PATs exist** — `identity.app.PersonalAccessTokenService` implements it (hashing + repository lookup + revocation/expiry check + touching `lastUsedAt`); `common.security`'s own code contains no import of anything in `identity`. | `common` is the shared kernel every module depends on, never the reverse (`CLAUDE.md`'s own architecture rule) — JWT validation fits that today only because it needs *no database lookup at all* ("the token is proof of identity," `CurrentUserArgumentResolver`'s own javadoc). PAT validation inherently needs one (hash lookup, revocation, expiry), so it can't be a pure-crypto `common` concern the same way. Declaring the contract in `common` and letting `identity` implement it (a plain Spring `@Component` satisfying an interface its own dependency, `common`, declares) is the same dependency-inversion shape `SecurityConfig` already uses to reach `assistant`'s own rate-limit config by string key rather than by import (M8 D11) — crossing the boundary via a declared contract, never a reverse import. |
| D16 | **A dedicated `OncePerRequestFilter` (`PersonalAccessTokenAuthenticationFilter`, `common.security`) recognizes a PAT by a fixed literal prefix (`kairon_pat_`) and runs *before* `BearerTokenAuthenticationFilter`; a custom `BearerTokenResolver` returns `null` for PAT-prefixed tokens so the OAuth2 resource server's own JWT-decode path never even attempts (and fails) to parse one as a JWT.** A successful PAT match sets a `PatPrincipal(userId, tokenId)` principal with exactly one granted authority, `SCOPE_mcp`; `CurrentUserArgumentResolver` is extended to resolve `@CurrentUser UserId` from either a `Jwt` (existing) or a `PatPrincipal` (new). | The existing JWT path is entirely unmodified — a different filter, ordered earlier, handles the different credential shape, and the custom `bearerTokenResolver` is the standard Spring Security extension point for "this bearer token isn't a JWT at all, don't try." Reusing `@CurrentUser UserId` for both credential types (rather than a second argument-resolver annotation) means every existing controller method signature needs no change at all to also accept PAT-authenticated calls. |
| D17 | **`SecurityConfig`'s `authorizeHttpRequests` expresses the PAT scope boundary (D3) as: explicit allow rules for the allowlisted paths first (matched by either credential, since `authenticated()` is satisfied by both), then a catch-all rule requiring "authenticated AND NOT `SCOPE_mcp`" for everything else** (`AuthorizationManagers.allOf(authenticated(), AuthorizationManagers.not(hasAuthority("SCOPE_mcp")))`). | Spring Security's `authorizeHttpRequests` evaluates matchers top-down, first match wins — so the allowlisted paths' rule has to come *before* the generic `/api/v1/**` rule, and that generic rule then has to positively exclude a PAT-authenticated principal rather than only excluding what the allowlist already matched (a PAT request to e.g. `PATCH /me` doesn't match any allowlisted-path rule above it, so it falls through to the catch-all — which must deny it explicitly, since plain `authenticated()` would otherwise let it through). This is the single most novel piece of this milestone's security design — flagged as a build-time verification spike, not an implementation detail to trust from the plan alone (Q2). |
| D18 | **No new `assistant_suggested_*` table and no change to any existing one.** A write-back's `PROPOSED` row uses the exact same `AssistantSuggestedTask`/`AssistantSuggestedProject`/`AssistantSuggestedProjectEdit` entities, repositories, capping (`maxSuggestions`/`maxTasks`/`maxOperations`), and category-resolution logic the Anthropic-API path already uses — extracted, not duplicated (D19). | Every one of these rows already means exactly "a proposed change awaiting the user's accept/dismiss, from *some* run" — nothing about where the run's content came from changes what the row means or how the existing review UI renders it. |
| D19 | **Two small extractions out of the already-large `AssistantRunService`, shared with a new `McpAssistantService`**: `AssistantAvailability` (the five `requireXAvailable` checks + `resolveModel`) and `AssistantSuggestionWriter` (`saveSuggestions`/`saveSuggestedProject`/`saveSuggestedEdit`/`capProjectEditOperations`/`resolveCategory`/`normalizeParentKeys`/`clampToRange`), both new package-private `@Component`s in `assistant.app`, injected into both services. | Same precedent M9.5's `CategoryResolver` extraction already set — "extracted… so `ProjectEditApplyService` can reuse it too, rather than duplicating it." Without this, every capping/resolution rule added by a future milestone would need to be kept in sync by hand across two services; with it, there's exactly one place each rule lives, read by whichever entry point needs it. |
| D20 | **`McpAssistantService` is a new class, not more methods bolted onto `AssistantRunService`.** It owns exactly the ten new endpoints' logic (five context-reads, five write-backs), depending on `AssistantAvailability`/`AssistantSuggestionWriter` (D19) and the five existing `*ContextBuilder`s, but never calling `AnthropicClient` at all. | `AssistantRunService` is already the single largest class in this module; a second concern (the MCP entry point) with its own fully-distinct lifecycle (no `PENDING`/`RUNNING` transition, no Anthropic call, no budget check) reads more clearly as its own class than as five more `request*`-shaped methods interleaved with the existing ones. |

## 3. Data model — new migration `V012__mcp_access.sql`

```sql
CREATE TABLE personal_access_token (
    id            UUID PRIMARY KEY,
    user_id       UUID NOT NULL REFERENCES app_user(id),
    name          VARCHAR(100) NOT NULL,
    token_hash    VARCHAR(64) NOT NULL UNIQUE,
    last_used_at  TIMESTAMPTZ,
    expires_at    TIMESTAMPTZ,
    revoked_at    TIMESTAMPTZ,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_personal_access_token_user
    ON personal_access_token (user_id) WHERE revoked_at IS NULL;

ALTER TABLE assistant_run ADD COLUMN source VARCHAR(10) NOT NULL DEFAULT 'API'
    CHECK (source IN ('API', 'MCP'));
```

No soft delete on `personal_access_token` — a revoked token is marked
`revoked_at`, never deleted, so "who had access and when" stays auditable
(same reasoning `RefreshToken` already follows, modulo its rotation
machinery, which a PAT has no equivalent of — D2). `source` defaults `'API'`
so every existing and future API-path row needs no backfill and no app-code
change beyond the new column's presence.

`PersonalAccessTokenAuthenticationFilter` (new `OncePerRequestFilter`):

```java
public class PersonalAccessTokenAuthenticationFilter extends OncePerRequestFilter {

    public static final String PREFIX = "kairon_pat_";

    private final PersonalAccessTokenValidator validator;

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String header = req.getHeader(HttpHeaders.AUTHORIZATION);
        if (header != null && header.startsWith("Bearer " + PREFIX)) {
            String raw = header.substring("Bearer ".length());
            validator.validate(raw).ifPresentOrElse(pat -> {
                var auth = new UsernamePasswordAuthenticationToken(pat, null,
                        List.of(new SimpleGrantedAuthority("SCOPE_mcp")));
                SecurityContextHolder.getContext().setAuthentication(auth);
            }, () -> {
                // leave context empty — falls through to the normal 401 entry point
            });
        }
        chain.doFilter(req, res);
    }
}
```

A custom `BearerTokenResolver` (registered via
`.oauth2ResourceServer(oauth2 -> oauth2.bearerTokenResolver(resolver))`):
returns `null` (no bearer token found) for any `Authorization: Bearer
kairon_pat_…` header, so `BearerTokenAuthenticationFilter` — which runs
*after* the filter above (`addFilterBefore`) — never attempts to decode a
PAT as a JWT; for every other header shape it delegates to
`DefaultBearerTokenResolver`, unchanged.

`CurrentUserArgumentResolver` gains one branch:

```java
Authentication authentication = SecurityContextHolder.getContext().getAuthentication();
Object principal = authentication == null ? null : authentication.getPrincipal();
return switch (principal) {
    case Jwt jwt -> UserId.fromString(jwt.getSubject());
    case PatPrincipal pat -> pat.userId();
    default -> throw new ResponseStatusException(UNAUTHORIZED, "Authentication required");
};
```

`SecurityConfig.securityFilterChain` gains (D17):

```java
.authorizeHttpRequests(auth -> auth
        .requestMatchers("/api/v1/auth/**", "/api/v1/ping").permitAll()
        // … existing actuator/swagger rules, unchanged …
        .requestMatchers(HttpMethod.GET, "/api/v1/todo/**", "/api/v1/journal/**", "/api/v1/projects/**")
            .authenticated()
        .requestMatchers("/api/v1/assistant/mcp/**").authenticated()
        .requestMatchers("/api/v1/**").access(AuthorizationManagers.allOf(
                AuthenticatedAuthorizationManager.authenticated(),
                AuthorizationManagers.not(AuthorityAuthorizationManager.hasAuthority("SCOPE_mcp"))))
        .anyRequest().permitAll())
.addFilterBefore(patFilter, BearerTokenAuthenticationFilter.class)
```

A PAT-authenticated request to an allowlisted path stops at one of the first
two new rules (both satisfied by `authenticated()`, which a PAT principal
is). A PAT-authenticated request to anything else — `PATCH /me`, `POST
/todo`, the *existing* `/assistant/todo-suggestions`, any accept/dismiss
endpoint — falls through to the final catch-all, which a `SCOPE_mcp`
authority explicitly fails; a JWT-authenticated request (no `SCOPE_mcp`
authority) passes that same final rule exactly as it does today, unchanged.

## 6. The MCP server (`mcp-server/`)

```
mcp-server/
├── package.json          @modelcontextprotocol/sdk, express (or Node's own http),
│                          zod (tool input schemas)
├── tsconfig.json
├── src/
│   ├── index.ts           creates one McpServer instance's tool registrations,
│   │                      wires an HTTP server using StreamableHTTPServerTransport,
│   │                      listens on a fixed port (e.g. 3000) inside the container;
│   │                      sends a periodic SSE keep-alive comment (~20-25s) on the
│   │                      long-lived GET/SSE half of the connection (Q5 mitigation —
│   │                      needed regardless of whether Funnel itself has an idle
│   │                      timeout, since ingress-nginx's own does too)
│   ├── auth.ts            per-request: reads Authorization: Bearer <token> off the
│   │                      incoming HTTP request; 401s before any tool handler runs
│   │                      if it's missing (D1-auth) — no token stored anywhere
│   ├── config.ts          reads KAIRON_BASE_URL from env (the in-cluster Service
│   │                      DNS name, D1-chart) — no KAIRON_PAT env var any more;
│   │                      there is no server-wide credential to configure
│   ├── kaironClient.ts    fetch wrapper: takes the per-request bearer token as a
│   │                      parameter (not a module-level constant — D1-auth), JSON
│   │                      in/out, maps Kairon's RFC 7807 problem+json body to a
│   │                      tool error (the third client to parse this shape, after
│   │                      web's client.ts and Android's ProblemDetail/AppError, M11.7)
│   └── tools/
│       ├── assistantContext.ts   the five get_*_context tools
│       ├── assistantSubmit.ts    the five submit_* tools
│       └── generalReads.ts       list_todos, get_journal_entries, list_projects,
│                                  get_project, list_project_tasks, … (D6 — thin
│                                  wrappers over the existing REST endpoints)
└── README.md              setup: generate a PAT in Account → Developer access;
                            in Claude Code, add a remote HTTP MCP server pointing at
                            https://xbmc.tail9ae0e9.ts.net/mcp with an Authorization
                            header carrying that PAT (exact CLI/config syntax
                            confirmed at implementation time against the real
                            client — this is Q7's open risk, not yet verified)
```

Each `submit_*` tool's input schema requires the caller (Claude Code,
reasoning on the user's behalf) to supply exactly the fields the matching
`POST /assistant/mcp/...` endpoint needs — the tool description text is
where the "you must have called the matching `get_*_context` tool first and
based your answer only on what it returned" instruction lives, mirroring
each `*ContextBuilder`'s own system-prompt rules (no invented tasks, no
invented urgency, etc.) for the benefit of whichever model is driving the
MCP client, since Kairon's own system prompt text is returned by the context
tool but nothing forces the calling model to honor it the way a direct
Anthropic API call's own `system` parameter does.

Every tool handler receives the current request's bearer token (threaded
through from `auth.ts`, D1-auth) and passes it straight to `kaironClient` for
every backend call it makes — there is no handler anywhere that reads a
token from `config.ts` or any module-level variable, which is the concrete
rule that keeps two concurrent users' requests from ever touching each
other's data.

## 10. ADR-0002 amendment (to make explicitly, not just note here)

This milestone changes two load-bearing sentences in ADR-0002 as written:

- **"All calls are server-side."** No longer true without qualification —
  the *reasoning* for an MCP-submitted result happens inside the user's own
  local Claude Code session, outside the instance entirely. What stays true,
  and is the actual invariant worth re-stating: **every call that spends
  the instance's own Anthropic budget is server-side**; the MCP path spends
  none of it (D5).
- **"A single `ANTHROPIC_API_KEY`… serves all users."** Still true for the
  original path; now there's a second path with no API key involvement at
  all. The real continuity is ADR-0002's *suggest-only* decision, which this
  milestone leaves completely intact (D4) — that's the sentence to point to
  as "what didn't change," not the server-side-calls one above.

Add a new ADR row to the alternatives table or a short "Amendments" section
(exact placement decided at implementation time) rather than editing the
original Decision prose out from under its own history — this repo's
existing ADRs don't appear to have needed a revision like this yet, so the
convention (append vs. edit-in-place) is itself worth a quick look at how
other ADRs in `docs/adr/` have evolved, if any have.
