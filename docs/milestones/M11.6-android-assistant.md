# M11.6 — Android: assistant features & settings — implementation plan

Status: **Accepted — implemented**. Companion to [`../ROADMAP.md`](../ROADMAP.md) (M11.6
acceptance criteria), [`../DESIGN.md`](../DESIGN.md) §12/§13 (Mobile,
Assistant), and [`../DATA_MODEL.md`](../DATA_MODEL.md). Follows the structure
and conventions of [`M11-android-foundation.md`](M11-android-foundation.md)
and [`M11.5-android-journal-projects.md`](M11.5-android-journal-projects.md)
— same split-vertical-slice reasoning, same decision-table format.

M11.6 is the third of the three Android slices (M11 → M11.5 → M11.6). Like
M11.5, it needs **no new backend work at all**: every endpoint this plan
consumes (`/assistant/todo-suggestions`, `/assistant/project-plan`,
`/assistant/project-edits`, `/assistant/summaries`,
`/assistant/journal-reflection`, `/assistant/runs`, the four
`suggested-*:accept`/`:dismiss` pairs, and `PATCH /me` for settings) already
shipped in M8/M8.5/M9/M9.5/M10, and the generated Kotlin client already has
every one of the six controllers this plan touches
(`AssistantRunControllerApi`/`ProjectPlanControllerApi`/
`ProjectEditControllerApi`/`SuggestedTaskControllerApi`/
`SuggestedProjectControllerApi`/`SuggestedProjectEditControllerApi`) from a
spec that hasn't changed shape underneath them. This milestone is
Android-only: five new feature entry points wired into existing screens, one
new history/detail destination, and an assistant-settings section on the
Account screen.

*(User decisions locked for this slice, same spirit as M11/M11.5's own
upfront calls — see §2 for the full rationale on each: a new "Summaries"
entry joins the top-bar overflow menu rather than the bottom nav; assistant
settings are an embedded section on the Account screen, not a new screen;
the project-plan/project-edit review screens get full exclude-with-cascade
parity with web, not a simplified accept-all/dismiss-only cut; journal
reflection's opt-in gets the same confirmation-dialog friction web gives it.)*

---

## 1. Scope

### In

- **Todo suggestions (M8)**: a "Suggest todos" entry point on the Today
  screen and the Day view (Todo tab) — a two-step dialog (horizon choice,
  then a review-and-accept list), mirroring web's `SuggestTodosButton`/
  `SuggestedTaskList`. Shown only when `assistant.todoSuggestions.enabled`.
- **AI project generation (M8.5)**: a "New project from description" entry
  point on the project list screen — description+dates form, then a
  review screen with the plan's task tree, milestone markers, a resolved
  category badge, and per-task include/exclude checkboxes that cascade from
  parent to children (D3/D9). Shown only when
  `assistant.projectGeneration.enabled`. Accepting navigates to the new
  project's detail screen, same as web.
- **AI project editing (M9.5)**: an "Edit with AI" entry point on the
  project detail screen — a free-text description form, then a diff-review
  screen grouped by change type (project fields, tasks added/updated/
  removed, dependencies added/removed, reordering) with per-change
  include/exclude checkboxes cascading from an excluded new task to anything
  else in the diff referencing its key (D3/D9). Shown only when
  `assistant.projectEditing.enabled`.
- **Weekly/monthly execution summaries + weekly journal reflection
  (M9/M10)**: a new **Summaries** screen (history list, "Generate
  weekly/monthly summary" buttons, and — when
  `assistant.journalReflection.enabled` — a "Generate weekly reflection"
  button), reached via the top-bar overflow menu (D1). Selecting a run opens
  a detail dialog rendering the run's markdown narrative (+ the
  deterministic stats table for summary runs), polling at a fixed interval
  while the run is still `PENDING`/`RUNNING` (D8).
- **Assistant settings**: a new section embedded on the Account screen (D2)
  — five per-feature opt-in toggles, a tone selector (encouraging/balanced/
  direct), and a model-override selector, read-modify-writing
  `preferences.assistant` via `PATCH /me` (D7). Enabling journal reflection
  specifically opens a confirmation dialog first, naming that full journal
  text is sent to Anthropic (D4) — the other four toggles commit immediately,
  same as web.
- One new dependency: a small Compose markdown renderer, needed to render a
  summary/reflection run's narrative + GFM table legibly (D6) — the Android
  equivalent of web's own M9 D17 (`react-markdown` + `remark-gfm`).
- Tests: ViewModel unit tests (MockK/Turbine) for the request/accept/dismiss
  flows and the cascade-exclusion logic, Compose UI tests for the new
  screens/dialogs — same shape as M11/M11.5's own test tables.

### Out (deferred, with what picks it up)

- **Any backend change.** Confirmed in §4 — every endpoint and DTO shape
  this plan needs already exists and is already reflected in the committed
  OpenAPI spec / already-generated Kotlin client.
- **Offline queueing of assistant requests.** Same posture as every other
  M11-family write (M11 D2) — every call below is online-required, plain
  error on failure, no retry queue.
- **Local (Room) caching of `assistant_run`/`assistant_suggested_*` rows.**
  Those tables are hard-delete-only and never appear in the `/sync` feed
  (`DATA_MODEL.md`'s own convention, confirmed unchanged by M8–M10) — there
  is nothing to cache. Every assistant screen is a live fetch, same "no
  natural offline need" reasoning M11 already applied to `today`/`about`
  and M11.5 applied to the project list (D5/D11 below).
- **M10.5 (MCP server / bring-your-own Claude subscription).** Still
  undrafted on the backend side (`ROADMAP.md`) and entirely orthogonal to
  this slice — Android only ever talks to the existing per-token
  `ANTHROPIC_API_KEY`-backed REST endpoints, regardless of how a future
  MCP path might also populate the same rows.
- **A dedicated `SummaryDetail` screen/route.** It's a dialog on top of the
  Summaries screen, same as web — no new nav route needed (D1's own
  reasoning: keep the nav graph this milestone touches as small as
  possible).

## 2. Decisions locked for this milestone

| # | Decision | Rationale |
| --- | --- | --- |
| D1 | **A new "Summaries" entry joins the top-bar overflow menu** (now Account/About/Summaries), reached from every top-level screen via `KaironBanner`'s existing `OverflowMenu`. Todo-suggestions, project-generation, and project-editing stay embedded as entry points on their existing host screens (Today/Todo, Project list, Project detail) — they're not separate destinations at all, same as web never gave them their own nav entry either. *(User decision.)* | Bottom nav is already at Material3's upper comfortable bound (M11.5 D3: Today/Todo/Journal/Projects); a 5th item would crowd it further for a screen (summary history) that's checked occasionally, not daily. The overflow menu is exactly the "secondary, tucked away" surface M11.5 D3 already designated for Account/About, and Summaries fits that same usage pattern. |
| D2 | **Assistant settings are an embedded section on the existing `AccountScreen`**, not a new screen. *(User decision.)* | Mirrors web exactly (`AssistantSettings` embedded in `AccountPage`). Account is already one tap away via the overflow menu, so this adds zero new nav surface — consistent with D1's "don't grow the nav graph for this milestone" theme. |
| D3 | **The project-plan and project-edit review screens get full parity with web's per-item exclude-with-cascade checkboxes** (`ProjectPlanReview`/`ProjectEditReview`), not a simplified accept-all/dismiss-only cut. *(User decision.)* | Unlike M11.5's tap-vs-drag scope-downs (a genuinely different *interaction model* with no UX loss), dropping per-item exclusion here would be a real capability gap — a user who wants 9 of 10 proposed tasks would otherwise have to dismiss the whole plan and re-prompt. The underlying accept-time cascade is already a pure function on data the generated client already returns (D9), so the added Compose UI work is checkbox-list rendering, not new logic. |
| D4 | **Enabling journal reflection opens a confirmation dialog** naming that full journal text (not a summary) is sent to Anthropic, matching web's M10 D13 treatment exactly; disabling it, and every other toggle, commits immediately with no confirmation. *(User decision.)* | Consistency with web's own deliberately-asymmetric friction for the one feature that sends raw journal content rather than structured task/project data — the risk profile is the same regardless of client, so the UI friction should be too. |
| D5 | **No new Room entities or DAOs.** `assistant_run`, `assistant_suggested_task`, `assistant_suggested_project`, and `assistant_suggested_project_edit` are hard-delete-only and were never added to the `/sync` feed by M8–M10 (confirmed by reading the current backend — `planning.app.SyncType`/`SyncService` still cover only `todo`/`journal`/`project`/`projectTask`). Every assistant screen (Summaries history, review screens) is a live fetch straight to the generated client. | Nothing here changed since M11.5 confirmed the same thing for `project_category`/`task_dependency` (M11.5 D-out) — a hard-delete, unsynced table has no `changedSince` story to begin with, so there's no caching decision to make, just a confirmation that none is needed. |
| D6 | **One new dependency: a Compose markdown renderer** (`com.mikepenz:multiplatform-markdown-renderer-m3`, CommonMark + GFM tables, Material3-themed) renders a run's `outputMarkdown` (narrative +, for summary runs, the deterministic stats table appended by the backend). | Raw markdown text (literal `#`/`**`/`\|` pipe characters) is unreadable, especially for a GFM table — exactly the problem web's own M9 D17 solved by adding `react-markdown`+`remark-gfm` specifically for this screen. This is the direct Android-equivalent single-purpose addition, not a general-purpose editor or a WYSIWYG component (contrast M11.5 D1, which deliberately avoided adding a *writing* dependency for journal entries — this is read-only rendering of model-authored and our-own-code-authored text, a narrower need). |
| D7 | **A typed `AssistantPreferences` struct + a merge-write helper** reads `MeResponse.preferences["assistant"]` (generated as `Map<String, JsonElement>?`, per M11's own `patchGeneratedClient` fixup), defensively parses each of the five `{enabled}` sub-objects plus `modelOverride`/`tone` (missing or wrong-shaped falls back to `false`/`null`/`"balanced"` — the same defensive posture the backend's own `AssistantPreferenceMapper` already takes, so a brand-new account needs no special-casing), mutates one field, and serializes the whole `assistant` sub-object back into a `kotlinx.serialization.json.JsonObject` for the `PATCH /me` body. | Kotlin/kotlinx.serialization has no object-spread over a loosely-typed JSON map the way web's `{...prefs, ...patch}` does; a small typed wrapper around the `JsonElement` map is the simplest way to get the same read-modify-write semantics without hand-rolling `JsonObject` construction at every call site. |
| D8 | **Summary/reflection runs are polled** — a small suspend helper re-fetches `GET /assistant/runs/{id}` on a fixed 2-second interval (matching web's own `POLL_INTERVAL_MS`) while `status` is `PENDING`/`RUNNING`, stopping on `SUCCEEDED`/`FAILED`. **Todo-suggestion, project-plan, and project-edit requests stay single synchronous calls** — those three endpoints already block on the model call server-side (M8/M8.5/M9.5's own synchronous shape) and return a `SUCCEEDED` run with its suggestions already populated, exactly like their web dialogs do today. | Matches the backend's actual sync/async split exactly (`AssistantRunController`: `/todo-suggestions`, `/project-plan`, `/project-edits` return populated results immediately; `/summaries` and `/journal-reflection` queue a `PENDING` run and are always polled) — no new decision to make here, just porting web's existing `useAssistantRun`/`POLL_INTERVAL_MS` shape to a Kotlin coroutine. |
| D9 | **The accept-time cascade-exclusion logic is ported to Kotlin as the same pure functions web already has**: `effectiveExcludedTaskKeys` (a project-plan's excluded parent cascades to its children, keyed by the plan's own string `key`) and `excludedNewTaskKeys`/`isTaskExcluded` (a project-edit's excluded new-task `ADD` operation cascades to anything else in the diff referencing that task's `key`), operating on the generated client's `PlannedTaskView`/`TaskOperationView`/`DependencyOperationView`/`ReorderOperationView` models. The resulting `excludedTaskKeys`/`excludedOperationKeys` list is sent as-is to the existing `:accept` endpoints — no new backend logic, this is purely "compute the same list web's UI already computes, client-side." | Reuses an already-validated pure function (web's own `ProjectPlanReview.effectiveExcluded`/`ProjectEditReview.excludedNewTaskKeys`) rather than inventing a new exclusion model — D3's full-parity decision would be hollow without actually porting the logic that makes per-item exclusion safe to send. |
| D10 | **No repository/DAO layer for any assistant call.** ViewModels inject and call the generated `AssistantRunControllerApi`/`ProjectPlanControllerApi`/`ProjectEditControllerApi`/`SuggestedTaskControllerApi`/`SuggestedProjectControllerApi`/`SuggestedProjectEditControllerApi` directly, same as `ProjectListScreen`'s own live-fetch posture (M11.5 D10) and `Today`/`About` (M11 §6.5). | D5 already established there's no local cache to mediate through — a repository layer would exist only to wrap a single Retrofit call per method, adding indirection with no behavior. |
| D11 | **Each embedded entry point (`SuggestTodosEntryPoint`, the project-list "New project from description" button, the project-detail "Edit with AI" button) is a self-contained composable + small ViewModel pair that fetches `GET /me` itself to read its own feature flag, rendering nothing if disabled** — the host screen (`TodayScreen`/`DayViewScreen`/`ProjectListScreen`/`ProjectDetailScreen`) doesn't need its own `me`/preferences-reading logic, it just places the entry-point composable. No app-wide "current user preferences" cache is introduced. | `GET /me` is a tiny, infrequently-changing payload — the same "small reference set, just refetch" reasoning M11.5 D10 already applied to `project_category`. A shared preferences cache/singleton would be new app-wide architecture this milestone doesn't otherwise need; four cheap independent calls is the simpler choice, consistent with D10's "no new layer" theme, and it keeps each entry point droppable into any screen without a host-side wiring step. |

### 5.2 Entry points on existing screens

- `TodayScreen` and `DayViewScreen` each place a `SuggestTodosEntryPoint(day
  = <that screen's date>)` — self-contained per D11, renders nothing if
  `assistant.todoSuggestions.enabled` is false.
- `ProjectListScreen` places a `ProjectGenerationEntryPoint()` near its
  existing "New project" action.
- `ProjectDetailScreen` places a `ProjectEditEntryPoint(projectId)` near its
  existing "Edit"/"Delete" actions — needs that screen's already-loaded
  `ProjectTaskDao`/dependency data (same data `TaskEditScreen`'s
  `DependencySection` already reads) to render task/dependency names in the
  review screen instead of bare ids, mirroring web's `EditProjectDialog`
  fetching the project's current tasks/dependencies for exactly that reason.

### 5.3 Summaries screen & settings (D1/D2)

- `OverflowMenu` gains a third `DropdownMenuItem("Summaries")`; `KaironBanner`
  gains an `onSummaries` callback alongside its existing `onAccount`/
  `onAbout`; `KaironNavHost` gains one new route, `Route.Summaries`, routed
  the same way `Route.Account`/`Route.About` are today (no bottom-nav
  change).
- `SummariesScreen`: `GET /assistant/runs?kind=WEEKLY_SUMMARY,MONTHLY_SUMMARY[,JOURNAL_REFLECTION]`
  (the third kind only requested when `assistant.journalReflection.enabled`,
  mirroring web's own `isJournalReflectionEnabled`/`summaryKinds` logic —
  this screen does its own `GET /me` check for that one flag, same D11
  posture), rendered as a history list; "Generate weekly/monthly summary"
  buttons call `POST /assistant/summaries`, a "Generate weekly reflection"
  button (shown only when opted in) calls `POST /assistant/journal-reflection`;
  either success opens `SummaryDetailDialog` for the new run immediately.
- `SummaryDetailDialog`: while `status` is `PENDING`/`RUNNING`, shows a
  spinner and polls (D8); once `SUCCEEDED`, renders `outputMarkdown` via the
  new markdown renderer (D6); `FAILED` shows the run's `error` field.
- `AssistantSettingsSection` (embedded in `AccountScreen`, D2): five
  `Checkbox`-equivalent (Material3 `Switch` or `Checkbox`) rows wired to
  `AssistantSettingsViewModel`'s read-modify-write `PATCH /me` calls (D7);
  a tone dropdown (encouraging/balanced/direct) and a model-override
  dropdown (instance default / Sonnet 5 / Opus 5 / Haiku 4.5, matching web's
  `MODEL_OPTIONS`); toggling journal reflection **on** opens a confirmation
  `AlertDialog` first (D4), toggling it off or any other toggle commits
  immediately.

## 8. Open questions / risks

| # | Question | Notes |
| --- | --- | --- |
| Q1 | Does a 2-second fixed poll interval (D8) feel responsive enough on a phone screen with no other feedback, given M8.5's own ~90s observed project-plan... (that one's synchronous, not polled) — but a weekly/monthly summary's actual generation latency hasn't been measured on this codebase yet? | Leaning "fine" — it's the same interval and UX (spinner + poll) web already shipped with no reported complaint; revisit only if a real device shows it feels slow or wasteful. |
| Q2 | Should the `SuggestTodosEntryPoint`/`ProjectGenerationEntryPoint`/`ProjectEditEntryPoint`'s own `GET /me` flag-check (D11) be re-fetched every time the composable enters composition, or cached for the screen's lifetime? | Leaning re-fetch on enter (simplest, consistent with "cheap to refetch" reasoning) — only revisit if it's a noticeably chatty number of calls in practice once the whole screen is wired up. |

## 10. Corrections found during implementation

- **D6 (markdown renderer) — scoped down to a hand-rolled renderer, §8 Q3's
  own named fallback taken rather than the `multiplatform-markdown-renderer-m3`
  dependency.** A clean spike against this project's pinned Compose/Kotlin/AGP
  versions wasn't practical to verify in this environment without a live
  Maven resolve against a brand-new dependency, and §8 Q3 had already flagged
  the risk and named the exact fallback to take if it didn't pan out: a
  small, purpose-built renderer covering only what the model and our own code
  actually emit. `assistant/MarkdownText.kt` parses headings, paragraphs with
  `**bold**` spans, bullet lists, and one GFM table shape (the deterministic
  stats table M9 appends) and renders them with plain Compose `Text`/`Row`/
  `Column` — no new Gradle dependency. Revisit if a future narrative shape
  needs more than this covers.

  exact ViewModel split may shift during implementation"): each embedded
  entry point (`SuggestTodosEntryPoint`/`ProjectGenerationEntryPoint`/

  with no further splitting needed.

  out of scope for this slice. Revisit as a follow-up if these flows need
