# M11.9 — Android: configurable notifications for overdue and incomplete items — implementation plan

Status: **Draft**. Companion to [`../ROADMAP.md`](../ROADMAP.md) (M11.9
acceptance criteria, alongside M11.7/M11.8's own inline-only entries there),
[`../DESIGN.md`](../DESIGN.md) §12/§14 (Mobile, open decisions), and
[`../DATA_MODEL.md`](../DATA_MODEL.md) ("Not in the first cut"). Follows the
structure and conventions of
[`M11.6-android-assistant.md`](M11.6-android-assistant.md) — same
decision-table format, same level of grounding in the actual current code.

M11.9 is Android-only and needs **no backend change at all** — both
notification conditions are computed entirely from data already cached
locally via `GET /sync` (`todo_item`, `project_task`). Unlike M11.5/M11.6's
"no backend work" claim, though, this one needs a genuinely new piece of
client infrastructure that doesn't exist yet anywhere in the app today: a
**periodic background job**. Every sync call today (`SyncRepository.sync()`)
is triggered by a screen's own `ViewModel` on-demand — there is no
`WorkManager` dependency, no background scheduling, and no
`POST_NOTIFICATIONS` permission declared anywhere in `mobile/android/`
(confirmed by inspection: `app/build.gradle.kts` has no `work-runtime`/
`hilt-work` entries, and `AndroidManifest.xml` declares only
`android.permission.INTERNET`). This plan adds all three.

*(User decisions locked for this slice — see §2 for the full rationale on
each: notification preferences are stored **on-device only**, not synced via
the backend, unlike assistant settings; delivery is **on-device scheduling
only** — no FCM, no `device_token`, no backend scheduler, the
`DATA_MODEL.md` "not in the first cut" stub for server-driven push stays
unbuilt.)*

---

## 1. Scope

### In

- **Two independent, configurable notification types**, both surfaced as a
  new "Notifications" section on the existing Account screen:
  1. **Daily incomplete-todo reminder** — if, at or after a user-chosen time
     of day, today's todo list (`TodoDao.listForDay(today)`) still has at
     least one item whose `status != "DONE"`, fire a local notification. At
     most one per calendar day.
  2. **Overdue project-task notification** — if any `project_task` row is
     overdue (`plannedEnd < today AND status != DONE`, the exact definition
     `ProjectsApi.dueOrOverdue`/`ProjectTaskRepository.findDueOrOverdue`
     already use server-side for the "due or overdue" half of that query),
     fire a local notification naming how many. Only fires for tasks not
     already notified about (no repeat spam for the same task across ticks).
  Each type has its own on/off toggle; the daily reminder also has a time
  picker (default `18:00`, device-local time). Both default to **off**.
- **A new periodic `WorkManager` job** (`NotificationCheckWorker`) that,
  roughly every 30 minutes while at least one toggle is on: calls the
  existing `SyncRepository.sync()` to refresh Room (constrained to
  `NetworkType.CONNECTED`; a failed/skipped sync just means that tick
  evaluates slightly-stale Room data rather than erroring), then evaluates
  both conditions above against the refreshed cache and fires whichever
  notification(s) are due.
- **New on-device-only preference storage** (`NotificationPreferences.kt`, a
  small Proto/Preferences DataStore, same mechanism precedent as
  `SyncCursorStore`) for: `dailyReminderEnabled`, `dailyReminderTime`,
  `overdueNotificationsEnabled`, plus two pieces of internal bookkeeping —
  `lastDailyReminderDate` (dedupe the daily digest) and
  `notifiedOverdueTaskIds` (dedupe the overdue digest).
- **The Android 13+ (`TIRAMISU`) `POST_NOTIFICATIONS` runtime permission
  request flow**, triggered the first time either toggle is turned on; a
  denial still saves the preference (the worker simply can't post until the
  user grants it from system settings — same "don't block on a permission
  the OS might deny" posture as any other Android permission flow).
- **Two notification channels** (`daily_reminder`, `overdue_tasks`) so a user
  can mute/configure either independently from Android's own per-channel
  settings, not just this app's toggles.
- **Tying the worker's lifecycle to the session**: enqueued (`KEEP` policy)
  on successful login/register and on app start if a session already exists;
  cancelled from `SessionClearer.clearSession()` — extending the same
  session chokepoint M11.5 already extended for its three new Room tables
  (closing the exact shape of gap M11.8 found for `todo`, applied here
  pre-emptively rather than after the fact).
- Tests: pure-function tests for the two notification conditions and the
  dedupe bookkeeping (no Android/WorkManager dependency), a
  `TestListenableWorkerBuilder`-based test for `NotificationCheckWorker`
  itself, and a `NotificationPreferences` DataStore round-trip test.

### Out (deferred, with what picks it up)

- **Any backend change.** Both conditions are computed entirely from
  already-synced Room data; `ProjectsApi`/`TodoApi` need no new port method.
- **Backend-driven push (FCM), `device_token` storage, a server-side
  scheduler.** *(User decision.)* Stays exactly where `DATA_MODEL.md`'s "Not
  in the first cut" section already left it — a stub, unbuilt. This would be
  the thing to reach for if local `WorkManager` scheduling (subject to
  Doze/battery-optimization timing drift, §8 Q1) proves too unreliable in
  practice, or if iOS is ever added (there is no iOS app planned, per
  `CLAUDE.md`, so that's not a live driver today).
- **Cross-device-synced preferences.** *(User decision.)* A user with two
  Android devices configures notifications on each separately — no
  `app_user.preferences` field, no `PATCH /me` call, unlike every assistant
  toggle.
- **Deep-linking a notification tap to a specific task or project.** Tapping
  either notification just opens the app at its normal launch entry point
  (Today — already shows `DueTasksPanel` for overdue items and the day's
  todo list) rather than navigating to a specific task/project detail
  screen. A plausible follow-up once there's real usage to justify the extra
  nav-graph wiring.
- **Snoozing, per-project notification scoping, or a configurable check
  frequency.** Two on/off toggles and one time picker is the whole
  configuration surface this slice builds; anything finer-grained is
  backlog.
- **Web notifications.** Browser push/notifications for the web app aren't
  in scope here — this plan is Android-only, same as the rest of the
  M11-family.
- **A `BOOT_COMPLETED` receiver.** Not needed — `WorkManager`'s periodic work
  is backed by its own persistent store and reschedules itself after a
  reboot without any app-level receiver (confirmed: this is documented
  `WorkManager` behavior, not something this app has to implement).

## 2. Decisions locked for this milestone

| # | Decision | Rationale |
| --- | --- | --- |
| D1 | **Notification preferences live on-device only** (a new DataStore file), not synced via `PATCH /me`/`app_user.preferences`. *(User decision.)* | Keeps this slice entirely Android-side with zero backend/migration surface, unlike the assistant settings precedent. A user's notification preference is arguably inherently per-device anyway (whether *that phone* buzzes), so there's no clear case for cross-device sync forcing extra scope onto what would otherwise be a self-contained client feature. |
| D2 | **Delivery is on-device `WorkManager` scheduling only — no FCM, no `device_token`, no backend scheduler.** *(User decision.)* | Both conditions this slice needs are derivable entirely from data the device already has cached via `/sync`; a server-push mechanism would be solving a problem ("deliver while the app process is fully gone and Doze-restricted") this slice doesn't yet have evidence of needing. Matches `DATA_MODEL.md`'s own "not in the first cut" framing for the device-token/APNs-FCM stub — left as the fallback if §8 Q1's timing-drift risk turns out to matter in practice. |
| D3 | **The periodic job performs its own `/sync` call** (reusing the existing `SyncRepository.sync()` singleton unchanged) before evaluating either condition, rather than only reading whatever Room already has. | Nothing in the app today triggers a background sync — every existing call site is a screen's `ViewModel` reacting to that screen opening (confirmed: no `WorkManager`/periodic-sync code exists anywhere in `mobile/android/app`). Without this, a device that's been backgrounded for hours would evaluate stale data and could miss a task going overdue, or reassure a user who already completed their last todo from a different context the cache hasn't seen yet. |
| D4 | **A single `PeriodicWorkRequest` on a ~30-minute cadence** evaluates both conditions in one tick, rather than two separate workers or an exact-time `AlarmManager` alarm for the daily reminder. | `WorkManager`'s minimum periodic interval is 15 minutes; 30 minutes is a deliberately modest middle ground between timeliness and battery cost for what are both "reminders," not time-critical alerts. Using `AlarmManager.setExactAndAllowWhileIdle` for the daily reminder would get closer to the user's exact chosen time but requires the `SCHEDULE_EXACT_ALARM`/`USE_EXACT_ALARM` permission (extra Play Store scrutiny + a user-facing permission ask) for a feature where "within ~30 minutes of the chosen time" is an acceptable trade-off. Revisit (§8 Q1) if real usage shows the drift matters. |
| D5 | **The daily reminder fires at most once per calendar day** — the first tick at or after the configured time where at least one of today's todos is still incomplete — tracked via a stored `lastDailyReminderDate` compared against the device's current local date. **The overdue notification fires once per currently-overdue task** — a stored `notifiedOverdueTaskIds` set is diffed against the task ids `ProjectTaskDao`'s new overdue query currently returns each tick; only newly-appearing ids trigger a notification (batched into one if more than one newly overdue in the same tick), and ids no longer present (task completed, rescheduled, or deleted) are pruned from the stored set so a task can re-notify if it becomes overdue again later. | Without dedup, a 30-minute tick would re-notify for the same unfinished day or the same overdue task roughly 48 times a day — the two mechanisms above are the minimum bookkeeping needed to make this a "reminder," not a nag. Pruning the stored overdue-id set (rather than letting it grow forever) keeps it bounded and correctly allows a task to re-notify if its situation changes. |
| D6 | **Two notification channels** (`daily_reminder`, `overdue_tasks`), created once at app start (`NotificationManager.createNotificationChannel`, a no-op on re-creation). | Lets a user mute or re-prioritize either notification type from Android's own per-channel system settings independently of this app's own toggles — the standard Android pattern for "more than one logically distinct kind of notification," and a near-zero-cost addition once two notification types exist at all. |
| D7 | **Tapping either notification opens the app at its default launch entry point (Today), no deep link to a specific task/project.** *(Scope-down, named explicitly rather than silently dropped.)* | Today already surfaces both signals this feature is about (`DueTasksPanel` for overdue project tasks, the day's own todo list for incomplete items) — a user who taps the notification lands somewhere immediately relevant without this slice needing any new nav-graph/deep-link plumbing. |
| D8 | **The `NotificationCheckWorker`'s lifecycle is tied to the session**: `WorkManager.enqueueUniquePeriodicWork(..., ExistingPeriodicWorkPolicy.KEEP, request)` is called after a successful login/register and on app start if `TokenStore` already holds a valid session, and `WorkManager.cancelUniqueWork(...)` is added to `SessionClearer.clearSession()` alongside the existing token/Room/cursor clearing. | Without this, the job would keep firing a `/sync` call (and failing, repeatedly, once the refresh token is gone) every 30 minutes on a logged-out device forever. `SessionClearer` is already this codebase's established single chokepoint for "end a session, whatever triggered it" (M11.5's own extension of it for the journal/project/project-task DAOs) — extending it here is the same move, not a new pattern. |
| D9 | **No new Room entity.** `NotificationPreferences` is a small Preferences DataStore (same shape as `SyncCursorStore`'s own single-purpose DataStore), not a Room table — it's five scalar/primitive values with no relational shape and nothing else ever needs to join against it. | Matches `SyncCursorStore`'s existing precedent exactly (a cursor is conceptually the same kind of thing: a handful of small per-device state values, not a business entity). Introducing Room for this would be ceremony. |
| D10 | **`ProjectTaskDao` gains one new query** (`findOverdue(today: LocalDate): List<ProjectTaskEntity>`, `WHERE plannedEnd < :today AND status != 'DONE'`) rather than fetching every task and filtering in Kotlin. `TodoDao` needs no new query — `listForDay(today)` already exists and is filtered for `status != "DONE"` in the worker. | Mirrors the exact predicate the backend's own `ProjectTaskRepository.findDueOrOverdue` uses for its overdue half (`t.plannedEnd < :day AND t.status <> DONE`) — same definition of "overdue" on both platforms, computed where the data already lives (SQL/Room) rather than reimplemented as a Kotlin filter over every row. |

## 3. Data model

**No backend schema change.** Entirely new, entirely on-device:

- A new Preferences DataStore file (`notification_prefs`) holding:
  `dailyReminderEnabled: Boolean`, `dailyReminderTimeMinutes: Int` (minutes
  since midnight, device-local), `overdueNotificationsEnabled: Boolean`,
  `lastDailyReminderDate: String?` (ISO `LocalDate`), and
  `notifiedOverdueTaskIds: Set<String>` (task id strings).
- One new `ProjectTaskDao` query (D10); no Room schema/version bump needed —
  a new `@Query` method on an existing `@Entity` adds no column or table.

## 4. Backend

**None.** Both notification conditions are computed from data `GET /sync`
already delivers today (`todo`, `projectTask` — both already in
`SyncRepository.REQUESTED_TYPES` since M11.5). No new endpoint, no DTO
change, no OpenAPI spec change, no client regeneration needed.

## 5. Android

### 5.1 New dependencies

- `androidx.work:work-runtime-ktx` — `WorkManager` + Kotlin coroutine
  (`CoroutineWorker`) support.
- `androidx.hilt:hilt-work` (+ its annotation processor) — `@HiltWorker` so
  `NotificationCheckWorker` can constructor-inject `SyncRepository`,
  `TodoDao`, `ProjectTaskDao`, and `NotificationPreferences` the same way
  every other Hilt-managed class in this app already does.
- No new DataStore dependency — `androidx.datastore:datastore-preferences`
  is already a transitive/declared dependency via `SyncCursorStore`
  (confirm at implementation time; add explicitly if it turns out to be only
  transitive).

### 5.2 Project layout additions

```
mobile/android/app/src/main/java/com/kairon/android/
└── notifications/
    ├── NotificationPreferences.kt      DataStore-backed prefs + bookkeeping (D1/D5/D9)
    ├── NotificationConditions.kt        pure functions: isDailyReminderDue(), newlyOverdueTaskIds() (D5/D10)
    ├── NotificationChannels.kt         creates the two channels at app start (D6)
    ├── NotificationCheckWorker.kt       @HiltWorker CoroutineWorker: sync (D3) -> evaluate -> notify
    ├── NotificationScheduler.kt        enqueue/cancel helpers used by AuthRepository/KaironApplication/SessionClearer (D8)
    ├── NotificationsSection.kt         embedded in AccountScreen: 2 toggles + time picker + permission request (D1)
    └── NotificationsSettingsViewModel.kt
```

### 5.3 Permission flow

- `AndroidManifest.xml` gains `<uses-permission
  android:name="android.permission.POST_NOTIFICATIONS" />` (a no-op
  pre-`TIRAMISU`, required to even ask at runtime on 13+).
- `NotificationsSection` requests it (via
  `ActivityResultContracts.RequestPermission()`) the first time either
  toggle flips from off to on and the permission isn't already granted; a
  denial still persists the toggle's new on state (the worker's own
  `NotificationManagerCompat.areNotificationsEnabled()` check at post-time
  is the real gate — this is just the one-time ask).

### 5.4 Worker behavior (`NotificationCheckWorker`)

1. Read `NotificationPreferences`; if both toggles are off, return
   `Result.success()` immediately (cheap no-op tick).
2. Call `syncRepository.sync()` (D3); log and continue regardless of the
   `Result` — a failed sync just means step 3 evaluates whatever Room
   already has.
3. If `dailyReminderEnabled` and `isDailyReminderDue(now, prefs)` (D5): query
   `todoDao.listForDay(today)`, and if any item's `status != "DONE"`, post to
   the `daily_reminder` channel and update `lastDailyReminderDate`.
4. If `overdueNotificationsEnabled`: query `projectTaskDao.findOverdue(today)`
   (D10), diff against `notifiedOverdueTaskIds` (D5), post one notification
   to the `overdue_tasks` channel naming the newly-overdue count/titles if
   the diff is non-empty, and update the stored id set (add new, prune
   gone).
5. Return `Result.success()` unconditionally — a failure here should not
   trigger `WorkManager`'s own retry/backoff machinery for what is, at
   worst, a missed reminder tick that the next one 30 minutes later recovers
   from.

### 5.5 Settings UI

- `NotificationsSection` (embedded in `AccountScreen`, mirroring
  `AssistantSettingsSection`'s own "embedded section, not a new screen"
  precedent from M11.6 D2): a `Switch` for "Remind me about unfinished
  todos" with a time picker (`TimePickerDialog` or a Compose
  Material3 `TimePicker`) shown only when enabled, and a second `Switch` for
  "Notify me about overdue project tasks."
- `NotificationsSettingsViewModel` reads/writes `NotificationPreferences`
  directly (no repository indirection needed — same "no layer for a single
  small store" reasoning M11.6 D10 already applied to the generated
  assistant API clients) and triggers the permission request (§5.3) on an
  off→on toggle flip.

### 5.6 Session wiring (D8)

- `NotificationScheduler.enqueue(context)` — called from `AuthRepository`
  after a successful login/register, and from `KaironApplication.onCreate()`
  if `TokenStore` already reports a logged-in session (app relaunch with an
  existing session).
- `NotificationScheduler.cancel(context)` — called from
  `SessionClearer.clearSession()`, alongside the existing
  `tokenStore.clear()`/DAO/`syncCursorStore.clear()` calls.

### 5.7 CI

- `.github/workflows/android.yml` needs no structural change — the new
  `work-runtime-ktx`/`hilt-work` dependencies resolve through the existing
  `:app:testLocalDebugUnitTest :app:lintLocalDebug` tasks like any other
  dependency addition.

## 7. Task breakdown (suggested order)

1. Add `work-runtime-ktx`/`hilt-work` to `gradle/libs.versions.toml` and
   `app/build.gradle.kts`; add `POST_NOTIFICATIONS` to
   `AndroidManifest.xml`.
2. `notifications/NotificationPreferences.kt` + `NotificationPreferencesTest`
   — the DataStore and its five fields, default-off.
3. `ProjectTaskDao.findOverdue` (D10); `notifications/NotificationConditions.kt`
   + `NotificationConditionsTest` — the two pure condition functions and the
   dedupe/prune logic, against fake entity lists (no DB needed for this
   test).
4. `notifications/NotificationChannels.kt` — create both channels from
   `KaironApplication.onCreate()`.
5. `notifications/NotificationCheckWorker.kt` (`@HiltWorker`) +
   `NotificationCheckWorkerTest` — wire steps 2–4 together per §5.4.
6. `notifications/NotificationScheduler.kt`; wire `enqueue`/`cancel` into
   `AuthRepository`, `KaironApplication.onCreate()`, and
   `SessionClearer.clearSession()` (D8).
7. `notifications/NotificationsSection.kt` + `NotificationsSettingsViewModel`
   — embed in `AccountScreen`; wire the `POST_NOTIFICATIONS` permission
   request (§5.3) and the time picker.
8. Compose UI test for `NotificationsSection`.
9. Manual smoke test on a real device/emulator (notification delivery can't
   be fully verified by unit tests alone): enable the daily reminder with a
   near-future time, confirm it fires once and not again that day; enable
   overdue notifications with a project task whose `plannedEnd` is in the
   past, confirm one notification, confirm it isn't repeated on the next
   tick, confirm completing the task (or pushing its date forward) and later
   making another task overdue produces a fresh notification; deny the
   runtime permission and confirm the toggle still saves without crashing;
   force-stop the app and confirm the periodic work still fires (proving the
   session-tied enqueue/`KEEP` policy survives process death); log out and
   confirm no further sync/notification activity occurs.
10. Docs: tick `ROADMAP.md`'s M11.9 boxes; `DESIGN.md` §12 updated to note
    Android now has on-device notifications (§14's open decision already
    updated by this same change — re-confirm wording once implemented);
    `CLAUDE.md` "Current state" `mobile/android/` tree extended with the new
    `notifications` package; mark this plan `Accepted`.

## 8. Open questions / risks

| # | Question | Notes |
| --- | --- | --- |
| Q1 | Is a ~30-minute `WorkManager` cadence (D4) tight enough in practice, given real-world Doze-mode/battery-optimization batching can push actual execution noticeably later than the nominal interval on some OEM skins? | Leaning "acceptable for a reminder, not an alert" — revisit only if real usage surfaces reminders landing meaningfully (hours) late; the documented fallback is `AlarmManager.setExactAndAllowWhileIdle` for the daily reminder specifically (not the overdue check, which has no single "due instant" to target), accepting the `SCHEDULE_EXACT_ALARM` permission cost named in D4. |
| Q2 | Should the overdue notification be a single running digest ("3 tasks overdue," updated in place as the count changes) or a fresh notification per newly-overdue batch, left to stack in the notification shade? | Leaning "fresh per batch" (simpler — no notification-update/replace logic, no "is this the same logical notification" id-tracking beyond the dedupe set D5 already needs) — revisit if real usage shows notification-shade clutter is a problem. |
| Q3 | Does `SyncRepository.sync()` work correctly when invoked from a `CoroutineWorker`'s background process context — specifically, does the Hilt `EntryPoint`/constructor-injection path used by `@HiltWorker` actually get a fully-initialized `TokenStore` (in-memory access token empty on a cold process, refresh token present in `EncryptedSharedPreferences`) and correctly complete the existing 401→refresh→retry flow (`AuthAuthenticator`) with no foreground UI present? | Expected to work — `AuthAuthenticator` is a plain OkHttp `Authenticator`, UI-independent by construction, and the refresh token already persists past process death (confirmed: `TokenStore`'s access token is memory-only, but the refresh token is in `EncryptedSharedPreferences`, exactly the mechanism needed for a cold-started worker to re-authenticate). Verify with a real force-stop-then-fire test (§7 step 9) rather than assuming. |
| Q4 | Is a Compose Material3 `TimePicker` (stable since Compose Material3 1.2) available cleanly on this project's pinned Compose/AGP versions, or does it need a fallback to the platform `TimePickerDialog` (View-based, wrapped via `AndroidView`)? | Needs a quick check at implementation time against this project's pinned versions (same category of risk M11.6 §8 Q3 flagged for its markdown renderer, and which did in fact need a fallback there) — the platform `TimePickerDialog` is the named fallback if the Compose component doesn't fit cleanly. |
