# M8.5 — AI project generation from a description — implementation plan

Status: **Accepted — implemented.** Companion to [`../ROADMAP.md`](../ROADMAP.md) (M8.5 acceptance
criteria), [`../DESIGN.md`](../DESIGN.md) §13, [`../DATA_MODEL.md`](../DATA_MODEL.md),
and [`../adr/0002-ai-assistant-anthropic.md`](../adr/0002-ai-assistant-anthropic.md)
(this milestone adds a fourth assistant feature under that same ADR — it doesn't
revisit its decisions). Builds directly on the `assistant` module M8 established
(`AssistantRun` lifecycle, `AnthropicClient`, structured outputs, budget/rate-limit/
circuit-breaker plumbing) and reuses it unchanged; see D8 below for exactly what
carries over as-is.

Slotted as **M8.5** — between the already-implemented M8 and the still-unstarted
M9 — rather than renumbering. `ROADMAP.md`'s M9/M10/M11+ numbers, and every doc
that already cites them, stay put.

## 1. Scope

### In

- A fourth assistant feature: given a free-text project description plus a
  start date (required) and an optional target deadline, the LLM proposes a
  whole project — name, description, size, a ≤2-level task tree with
  milestones, per-task planned dates/estimates, and `FS`/`SS`/`FF`/`SF`
  dependencies between tasks.
- `PROJECT_GENERATION` added to `assistant_run.kind` (`V008` migration —
  widens the check constraint M8's `V007` didn't anticipate this value for).
- New table `assistant_suggested_project`: one row per run, the whole
  proposed plan stored as `jsonb`, `PROPOSED → ACCEPTED | DISMISSED`.
- New `ProjectsApi.createFromPlan` port method: one transactional call that
  creates the project, its task tree, and its dependency edges together —
  implemented by reusing `ProjectService.create`/`ProjectTaskService.create`/
  `TaskDependencyService.create` as internal collaborators (no duplicated
  entity-construction logic — same reuse principle as M8 D13).
- `POST /assistant/project-plan` (synchronous, like M8's todo-suggestions
  call), `POST /assistant/suggested-projects/{id}:accept` (body:
  `excludedTaskKeys`), `POST /assistant/suggested-projects/{id}:dismiss`.
- Web: a "New project from description" entry point on the project list, a
  form (free-text description + start date + optional deadline), a
  read-only review screen (project header + task tree with milestone
  markers + per-task checkboxes to exclude), and "Create project" landing
  the user on the normal `ProjectDetailPage` (Gantt included) they already
  know how to edit.
- A fourth per-feature opt-in, `assistant.projectGeneration.enabled`, on the
  existing `AccountPage` Assistant section.

### Out (deferred, with what would pick it up)

- **Inline editing of the proposed plan before creation** (renaming a task,
  dragging a date, changing an estimate) — decided with the user: review is
  include/exclude checkboxes only; adjustments happen after creation via the
  task-edit dialog and Gantt drag that already exist. Could become a later
  enhancement to this same review screen if checkbox-only proves too coarse
  in practice.
- **Deterministic forward-pass scheduling** (`DESIGN.md` §7.2, still an
  unscheduled backlog item — M7 D14). Not the same feature: that's an
  algorithmic recompute of dates from estimates + dependencies for an
  *existing* project; this milestone is the LLM proposing a first rough
  schedule when the project doesn't exist yet. The two don't conflict and
  could compose later (generate a plan here, then run forward-pass scheduling
  on it once that backlog item ships), but neither depends on the other.
- **Category assignment or color choice by the model** (D10) — the created
  project is uncategorized with the existing default color; the user sets
  both afterward exactly as they would for a manually-created project.
- **Regenerating / iterating on a rejected plan** ("try again with more
  detail") — dismiss and re-submit the form is the only loop for now; a
  tighter retry-with-feedback UX is a possible follow-up once real usage
  shows whether one-shot generation is good enough.

## 2. Decisions locked for this milestone

| # | Decision | Rationale |
| --- | --- | --- |
| D1 | **`PROJECT_GENERATION` requires a real migration** (`V008__project_plan.sql`: `ALTER TABLE assistant_run DROP CONSTRAINT assistant_run_kind_check`, re-add widened) — unlike M8's `TODO_SUGGESTION`, M8's `V007` only anticipated the four kinds `DATA_MODEL.md` already named at the time (`TODO_SUGGESTION`/`WEEKLY_SUMMARY`/`MONTHLY_SUMMARY`/`JOURNAL_REFLECTION`); this feature wasn't in that list. | No way around it — M8's D2 pre-widened for kinds already specified in `DATA_MODEL.md` at the time; this is a genuinely new kind the earlier milestone couldn't have anticipated. One more `ALTER … CHECK` is cheap and matches how `DATA_MODEL.md` itself keeps evolving. |
| D2 | **One `assistant_suggested_project` row per run, storing the whole plan as `jsonb`** (`plan` column: project fields + task list with `key` cross-references + dependency list), not a normalized per-task/per-dependency table set. `status` is `PROPOSED \| ACCEPTED \| DISMISSED`, same three values as `assistant_suggested_task`; `accepted_project_id` (FK → `project`, `ON DELETE SET NULL`) mirrors `accepted_todo_item_id`. | Unlike todo suggestions, individual tasks here don't need their own server-tracked accept/dismiss lifecycle — the whole project is created in one shot (D5). Normalizing into `assistant_suggested_project_task` / `assistant_suggested_dependency` tables would mean re-inventing most of `project_task`/`task_dependency`'s own shape inside `assistant` for rows that live for minutes and are then discarded — `jsonb` is the simpler fit for a short-lived, whole-document draft, consistent with the project's "simplest viable option" bias. |
| D3 | **One new port method, `ProjectsApi.createFromPlan(UserId, ProjectPlanCommand)`**, returning `ProjectView`. Implemented by a new `projects.app.ProjectPlanImportService` that calls `ProjectService.create`, then `ProjectTaskService.create` per task (roots first, then children, using a `key → UUID` map), then `TaskDependencyService.create` per edge — as ordinary Spring-bean-to-bean calls inside one `@Transactional` method, not new entity-construction code. | Same reuse discipline M8 D13 established for `TodoApi.create` on the accept path — one place mints a `project`/`project_task`/`task_dependency` row from cross-module code, and every existing invariant (≤2-level nesting, the milestone `plannedStart == plannedEnd` rule, position spacing, dependency cycle rejection) is enforced by the exact same code path a manual create/PATCH already goes through, not a second copy of those rules inside `assistant`. |
| D4 | **Input is free-text description + explicit `startDate` (required) + `targetDeadline` (optional) date fields** — not pure free text with dates left for the model to parse out of prose. *(User decision.)* | Confirmed with the user. Matches `DESIGN.md` §13.4's "the model narrates, numbers are computed/anchored first" principle applied to dates: an explicit `startDate` anchors every relative date the model proposes, instead of asking it to infer "today" or parse "in six weeks" out of prose — the least reliable part of an LLM's structured output is exactly this kind of date arithmetic. |
| D5 | **Review is include/exclude checkboxes only, no field editing before creation.** *(User decision.)* | Confirmed with the user, and matches their own framing ("I can adjust them later") — adjustments happen through the task-edit dialog and Gantt drag the app already has, not a new pre-create editor. Also matches M8's own review granularity (accept/dismiss per suggested item, no inline editing). |
| D6 | **Tasks and dependencies cross-reference each other by a short LLM-chosen string `key`** (e.g. `"t1"`), not a UUID — real ids don't exist until creation. `SuggestedProjectService.accept` builds a `key → UUID` map as it creates tasks in parent-before-child order, then resolves dependency edges against that map. Excluding a task (D5) **cascades to its children** (one hop is suf­ficient — the domain's own ≤2-level cap means there's never a grandchild) and to any dependency edge touching an excluded key. | The structured-output schema needs *some* way to express "task B depends on task A" and "task C is a subtask of task A" before any of them have real ids — string keys the model assigns itself are the natural fit (same shape `gantt-task-react`/most project-planning tools use internally). Cascading exclusion to children avoids ever creating an orphaned subtask whose parent the user explicitly unchecked. |
| D7 | **`kairon.assistant.project-plan.max-tasks`** (default 40) caps the task list after the response comes back, same enforcement style as M8 D5's suggestion cap (not a JSON-schema constraint — none exists in this SDK version). Dependency edges referencing an unknown/excluded key, or that would create a cycle, are **dropped and logged at `warn`**, not rejected as a failed run. | Bounds prompt/response cost and UI size for a runaway description ("plan my company's next five years"). The drop-and-log posture for bad edges matches M8 D10's general tolerance for imperfect LLM output over hard failures — one bad edge shouldn't block 39 good tasks from being created. |
| D8 | **Everything else is reused unchanged from M8**: the same `AnthropicClient` bean and circuit breaker (M8 D4/D6), the same per-user monthly token budget pre-flight check (M8 D8 — this feature draws from the same pool, no separate budget), the same `/assistant/**` Bucket4j rate limiter (M8 D11, no new filter instance needed — the path pattern already matches), the same 502/503 upstream-failure mapping (M8 D12), and the same **synchronous** run (M8 D7 — a plan with up to 40 tasks is still a single structured-output call, no more "slow" than a wide todo-suggestion request; async/polling stays deferred until M9 actually needs it for a real background job). | No reason to re-derive infrastructure M8 already built generically. The only genuinely new decisions this milestone makes are D1–D7 and D9–D12. |
| D9 | **A fourth per-feature opt-in preference**, `assistant.projectGeneration.enabled` (default `false`), alongside `todoSuggestions`/`executionSummaries`/`journalReflection` in `app_user.preferences.assistant` — no migration (still `jsonb`). `AssistantPreferencesView` gains a `projectGenerationEnabled` field. | `DESIGN.md` §13.5: "opt-in is per feature." A user who wants todo suggestions but not a project-generation feature that creates a whole tree of rows in one action should be able to leave the latter off. |
| D10 | **The model never chooses a project `category`, `color`, or `status`.** The created project always starts uncategorized, `DEFAULT_COLOR` (`ProjectService`'s existing default), and `status = PLANNING`. | Keeps the structured-output payload strictly about structure and schedule — the part only the model can usefully propose from a text description. Category/color are presentation choices the user already makes for every manually-created project; asking the model to guess one adds prompt surface for no real value (D10 companion to "Out" above). |
| D11 | **A violating nesting depth is corrected, not rejected**: if the model proposes a task nested under a task that is itself nested (a 3-level chain), the deeper task is flattened to top-level during import and the correction is logged at `warn`. The `plannedStart == plannedEnd` milestone invariant is enforced by the reused `ProjectTask.markMilestone` domain method exactly as it already is for manual creation — no separate check needed. | Same tolerant-degradation posture as D7/M8 D10. The ≤2-level rule is a hard domain invariant (`ProjectTaskService.validateParent`) the system prompt also states as a rule, but a model that occasionally over-nests shouldn't fail the whole run when a one-line correction fixes it. |
| D12 | **Authorization/error shape matches every other `assistant` endpoint**: `assistant_suggested_project` rows scoped `WHERE id = ? AND user_id = ?` (404 on missing/foreign), `409` if `:accept`/`:dismiss` is called on a row that isn't `PROPOSED`, `403` for disabled/opted-out/budget-exceeded (M8 D12's `ApiException.forbidden`), `502`/`503` for upstream failures. | Consistency with M8's `AssistantRunController`/`SuggestedTaskController` — no new error-handling code needed beyond what `GlobalExceptionHandler` already does. |

### 4.2 `projects.app.ProjectPlanImportService` (`@Service`)

```java
@Transactional
public ProjectView createFromPlan(UserId userId, ProjectPlanCommand command) {
    ProjectView project = projectService.create(userId, new ProjectService.CreateCommand(
            null, command.name(), command.description(), command.size(), null,
            command.startDate(), command.endDate()));

    Map<String, UUID> idByKey = new HashMap<>();
    List<PlannedTask> ordered = topLevelFirst(flattenExcessiveNesting(command.tasks())); // D11
    for (PlannedTask t : ordered) {
        UUID parentId = t.parentKey() == null ? null : idByKey.get(t.parentKey());
        ProjectTaskView created = taskService.create(userId, project.id(),
                new ProjectTaskService.CreateCommand(t.name(), t.description(), parentId,
                        t.plannedStart(), t.plannedEnd(), t.estimateHours(), t.isMilestone()));
        idByKey.put(t.key(), created.id());
    }

    for (PlannedDependency d : command.dependencies()) {
        UUID predecessorId = idByKey.get(d.predecessorKey());
        UUID successorId = idByKey.get(d.successorKey());
        if (predecessorId == null || successorId == null) {
            log.warn("Dropped dependency {} -> {}: unknown/excluded key, userId={}",
                    d.predecessorKey(), d.successorKey(), userId.value());
            continue;
        }
        try {
            dependencyService.create(userId, successorId,
                    new TaskDependencyService.CreateCommand(predecessorId, d.type(), d.lagDays()));
        } catch (ApiException e) { // cycle or other rejection — D7
            log.warn("Dropped dependency {} -> {}: {}", predecessorId, successorId, e.getMessage());
        }
    }
    log.info("Created project {} from plan userId={} tasks={} dependencies={}",
            project.id(), userId.value(), idByKey.size(), command.dependencies().size());
    return projectService.get(userId, project.id());
}
```

`flattenExcessiveNesting` (D11) walks the task list once: any task whose
`parentKey` points at another *non-root* task has its `parentKey` cleared
(logged at `warn`) before ordering. `topLevelFirst` is a stable partition —
roots, then children — sufficient because the domain's own ≤2-level cap
means there's never a third generation to schedule.

### 4.4 `ProjectPlanContextBuilder`

Much lighter than `TodoSuggestionContextBuilder` — this feature's only input
is what the user typed, not cross-module aggregation.

**System prompt** (constant, cacheable):

```
You are Kairon's project-planning assistant. Given a free-text project
description, propose a complete project: a short task tree, milestones, and
dependencies between tasks.

Rules:
- Keep tasks small and concrete — something a person can plan around, not a
  vague phase. Prefer more small tasks over fewer vague ones, but don't
  exceed a sensible task count for the described scope.
- At most one level of nesting: a subtask's parent must itself be top-level.
- A milestone is a zero-duration marker (plannedStart == plannedEnd) for a
  meaningful checkpoint — not every task's own finish date.
- Every date must fall within the project's overall start/end range stated
  in the user message. Never invent urgency or a deadline that isn't implied
  by the description or the stated range.
- Order and space planned dates sensibly given task dependencies — a
  successor's plannedStart should not fall before its FS predecessor's
  plannedEnd.
- Set dependencies only where the description implies a real ordering
  constraint, not for every consecutive pair of tasks.
```

**User content**:

```
Plan a project starting 2026-10-01[, targeting completion by 2026-12-15].
Today is 2026-09-25.

Description:
<the user's free text, verbatim>
```

Same caching reasoning as M8 §4.5: the system prompt carries no per-request
data, so its cacheable prefix never invalidates; `tone` is not read here for
the same reason M8 didn't read it for todo suggestions (a structural plan has
no room for tone the way a narrative summary does).

### 4.5 `AssistantRunService.requestProjectPlan`

Same shape as M8 §4.4's `requestTodoSuggestions`: `requireAssistantAvailable`
(now checking `prefs.projectGenerationEnabled()`), `requireWithinBudget`
(unchanged — same pool, M8 D8), create the `PENDING` → `RUNNING` run, call
`AnthropicClient.generateProjectPlan`, cap `plan.tasks()` at
`kairon.assistant.project-plan.max-tasks` (D7), persist the plan as a new
`AssistantSuggestedProject` (`PROPOSED`), `run.succeed(...)`, return a view
combining the run and the plan for review. Failures follow the identical
`AssistantUpstreamException` → `run.fail(...)` → rethrow path.

### 4.6 `SuggestedProjectService`

```java
@Transactional
public ProjectView accept(UserId userId, UUID id, List<String> excludedTaskKeys) {
    AssistantSuggestedProject row = require(userId, id); // 404
    requireProposed(row);                                 // 409 otherwise
    ProjectPlanPayload plan = parse(row.getPlan());
    Set<String> excluded = cascadeExclude(plan.tasks(), excludedTaskKeys); // D6
    ProjectPlanCommand command = toCommand(plan, excluded);
    ProjectView created = projectsApi.createFromPlan(userId, command);
    row.accept(created.id());
    log.info("Accepted project plan {} userId={} -> project {}", id, userId.value(), created.id());
    return created;
}

@Transactional
public AssistantSuggestedProjectView dismiss(UserId userId, UUID id) {
    AssistantSuggestedProject row = require(userId, id);
    requireProposed(row);
    row.dismiss();
    log.info("Dismissed project plan {} userId={}", id, userId.value());
    return mapper.toView(row);
}
```

`cascadeExclude` walks `plan.tasks()` once, adding any task whose
`parentKey` is in the caller's `excludedTaskKeys` (or was itself just added)
— one pass is enough given the ≤2-level cap (D6).

## 11. Corrections found during implementation

- **D3's constructor cycle.** `ProjectsApi.createFromPlan` has to live on
  `ProjectTaskService` (the interface's sole implementing bean — other
  modules inject `ProjectsApi` by type, so a second implementing bean would
  make that ambiguous), but the reuse the plan calls for means
  `ProjectPlanImportService` needs `ProjectTaskService` back. Broken with
  `@Lazy` on that one constructor parameter (a standard, narrow fix for
  exactly this "a layer needs to call back up" shape) rather than inlining
  the import logic into `ProjectTaskService` itself.
- **D8's rate-limit path.** "The path pattern already matches" turned out
  wrong — `kairon.assistant.rate-limit.paths` is a literal list matched by
  `AntPathMatcher`, not a `/assistant/**` wildcard already in place; `POST
  /assistant/project-plan` had to be added to that list explicitly in
  `application.yml`, alongside the existing `/assistant/todo-suggestions`
  entry.
- **No new response type needed.** Rather than the `ProjectPlanRunResponse`
  sketched in §4.7, `AssistantRunView` (M8) just gained a fourth-and-a-half
  field, `suggestedProject` (nullable, alongside the existing `suggestions`
  list) — one run view type serves both `POST /assistant/todo-suggestions`
  and `POST /assistant/project-plan`, each populating only the field
  matching its own kind.
- **Migration style.** Dropped the `DEFAULT now()` clauses from `V008`'s
  drafted SQL (§3) to match `V004`/`V005`/`V007`'s existing house style —
  Hibernate's `@CreationTimestamp`/`@UpdateTimestamp` already supply those
  columns at insert/update time, so a Postgres-side default was redundant
  and inconsistent with every other migration in this repo.
- **D11's milestone-date worry didn't materialize.** `ProjectTaskService.create`'s
  `applySchedule` calls `ProjectTask.markMilestone(date)` (a single date) for
  a milestone task, never `reschedule(start, end)` — so the
  `IllegalArgumentException` `reschedule` throws for mismatched
  `start`/`end` on a milestone can't actually be hit on the create path.
  Flattening excessive nesting (the real D11 case) still happens exactly as
  planned, in `ProjectPlanImportService` before any task is created.
