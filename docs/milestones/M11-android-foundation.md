# M11 — Android foundation: auth, sync & Today/Todo — implementation plan

Status: **Accepted — implemented** (see §11 for corrections found along the
way). Companion to [`../ROADMAP.md`](../ROADMAP.md) (M11
acceptance criteria), [`../DESIGN.md`](../DESIGN.md) §5 (API design) and §12
(Mobile), and [`../DATA_MODEL.md`](../DATA_MODEL.md) (soft-delete/`updated_at`
conventions this milestone finally puts to use).

M11+ as originally sketched in `ROADMAP.md` — a full-parity Android app
(auth, Today, Todo, Journal, Projects+Gantt, all five assistant features) plus
an offline write story — is not a vertical slice, it's the whole web app
again. This plan slices it the way M8→M8.5→M9→M9.5→M10 sliced the assistant
module: **M11** builds the Android app's entire foundation (project scaffold,
generated client, auth, the one generic sync mechanism every later screen
reuses) and proves it end-to-end with the two simplest features — Today and
Daily Todo. **M11.5** (Journal + Projects/Gantt) and **M11.6** (Assistant +
settings) follow, reusing this milestone's plumbing with no further
foundation work. See `ROADMAP.md` for the three sections' current shape.

*(User decisions locked for this slice: split into sub-milestones rather than
one M11 plan; ship online-required writes first and defer the offline
write-queue+replay to a later milestone — see D2.)*

---

## 1. Scope

### In

- A new `mobile/android/` Gradle project (its own `settings.gradle.kts`/AGP —
  **not** a subproject of the repo's root `:backend`/`:web` build, D7):
  Kotlin, Jetpack Compose (Material 3), Navigation-Compose, Hilt, Retrofit,
  Room, `androidx.security.crypto`.
- A generated Kotlin API client (OpenAPI Generator, `kotlin`/`retrofit2`
  target) from the backend's already-committed OpenAPI spec artifact (M7),
  regenerated by a new `task android-client`, drift-checked in CI the same
  way the web client already is.
- One new backend mechanism, **`GET /api/v1/sync`**, aggregating
  changed-since rows across `todo`, `journal`, and `projects` (D3), built now
  because every later screen (M11.5, M11.6) needs it, not because Today/Todo
  strictly require it on their own.
- `AuthResponse` gains a `refreshToken` field returned in the body (in
  addition to the existing web-only cookie), so a native client without a
  cookie jar can actually complete login (D6 — closes a real gap: today
  nothing ever returns one outside the cookie).
- Android screens: **Login/Register**, **Today** (todos + due project tasks,
  read-only + "add to today" promote + journal prompt — reuses
  `GET /planning/today` as-is), **Day view** (date-navigable todo list:
  quick-add, complete, reorder, rollover), **Account** (profile, timezone,
  logout/logout-all), **About** (`/actuator/info`).
- Local Room cache for todos, populated/kept current via `GET /sync`, used as
  the single source of truth the UI observes (read-through cache, D2) — not
  an offline write queue.
- A bottom-nav shell mirroring the web app's top-nav order for the screens
  that exist in this slice; no placeholder/disabled entries for
  Journal/Projects/Summaries (added as those milestones ship).
- A new CI workflow (`android.yml`), path-filtered to `mobile/**`, that
  doesn't slow down the existing backend/web `verify` job.

### Out (deferred, with what picks it up)

- **Offline writes.** Create/update/complete/reorder/delete all require
  connectivity and fail fast (a plain error, no local queue) if the device is
  offline (D2 — user decision). The local write-queue + replay-on-reconnect
  machinery `DESIGN.md` §12 eventually wants is its own later milestone, once
  this slice's basic shape (and real usage) has proven out the rest.
- **Journal, Projects/Gantt/dependencies, and all five assistant features**
  on Android — `M11.5`/`M11.6` (ROADMAP.md). `GET /sync`'s `journalEntries`/
  `projects`/`projectTasks` change-sets are built now (D3) but **unused** by
  the Android app until those milestones add the screens that consume them.
- **`task_dependency` in the sync feed.** That table has no soft delete
  (CLAUDE.md), so a changed-since scan can't see removed edges. Deferred to
  M11.5's own design — current lean (not locked) is "fetch
  `GET /projects/{id}/dependencies` live whenever a project detail screen is
  open," the same online-required posture D2 already sets for writes (D9).
- **Push notifications / reminders.** Not in `DESIGN.md`'s mobile section at
  all; no schema for it yet (`DATA_MODEL.md` "Not in the first cut").
- **A combined `mobile/android` + backend monorepo Gradle build.** Kept as
  two independent Gradle roots (D7) — no plan to unify them.
- **Full keyset pagination on `/sync`.** A generous per-type cap with a
  `truncated` flag instead (D5) — matches `DATA_MODEL.md`'s own "a
  sync-bookkeeping table if `since=` proves too coarse" escape hatch, not
  pre-built.
- **Instrumented/E2E Android tests against a running backend** (the
  Playwright-equivalent). Unit + Compose UI tests only this slice (§7); an
  instrumented pass is an open question (Q4), not committed.

## 2. Decisions locked for this milestone

| # | Decision | Rationale |
| --- | --- | --- |
| D1 | **M11 ships exactly: Android project scaffold + generated client, auth, the generic `/sync` mechanism, Today, Day/Todo, Account, About.** Journal/Projects/Gantt → M11.5; all assistant features + the assistant-settings screen → M11.6. *(User decision.)* | `CLAUDE.md`'s own principle — "each [milestone] ends with something running and deployable, not a half-built layer" — doesn't hold for one M11 covering the whole app. Today+Todo is the smallest pairing that (a) needs a real backend round-trip, (b) needs the sync/cache mechanism, and (c) ships something a user can actually use daily, mirroring M6's own "Today" scope precedent on the web side. |
| D2 | **Writes are online-required this slice; the local Room cache is read-through only** — populated by `GET /sync` plus each write's own success response, never replayed from a local queue. An attempted write while offline fails immediately with a plain "you're offline" error. *(User decision.)* | Keeps M11 to "one new generic mechanism" (sync-for-reads) instead of two (sync-for-reads + a write-queue/conflict-surfacing UI). The offline-write story in `DESIGN.md` §12 (client-generated ids, last-write-wins, `version` conflicts) is real but is its own later milestone once this one's shape is proven. |
| D3 | **`GET /api/v1/sync`** lives in the existing `planning` module (`planning.app.SyncService` / `planning.web.SyncController`, new files alongside the existing `PlanningService`/`PlanningController`), not a new top-level module. It aggregates one new port method per covered module — `TodoApi.changedSince`, `JournalApi.changedSince`, `ProjectsApi.changedSince`/`tasksChangedSince` — each returning a new shared `common.sync.ChangeSet<T>` (`{upserted: List<T>, deletedIds: List<UUID>, truncated: boolean}`). | `planning` is already this codebase's one precedent for "pure aggregation over `todo`/`projects`/`journal`, no own `domain`/`repo`" (M6 D1) — a sync aggregator is the same shape of module, and a new top-level module for a single endpoint would just be ceremony. `ChangeSet<T>` goes in `common` (the shared kernel) because it's generic infrastructure, not feature logic — same precedent as `common.id.Uuidv7`. |
| D4 | **The sync cursor is a single server-captured instant, not per-row bookkeeping.** `SyncService.changedSince` calls `Instant.now(clock)` **before** running any of the underlying queries and returns that as the response's `since` (the client's cursor for its *next* call), while querying every covered table with `updated_at >= <the client's previous since>`. | Guarantees no change is ever missed, including one that lands mid-request: because the returned cursor is captured strictly before the queries run, any row touched between capture and query execution is simply included again (harmless — upserts/tombstones are idempotent) rather than silently skipped. A per-row `nextCursor` scheme avoids the one wasted re-fetch but adds real complexity for no visible benefit at this app's scale. |
| D5 | **No pagination loop.** Each covered type is capped at a generous limit (default `500`, `kairon.sync.max-rows-per-type`); if more rows than that changed since the cursor, the response sets that type's `truncated: true` and logs a `warn`, but still returns `200` — it never fails the call. | `DATA_MODEL.md` already names the honest fallback ("a sync-bookkeeping table if `since=` proves too coarse") as a *later* concern, not a day-one requirement — this is a single-user-scale personal app; a user crossing 500 changed todo rows between two app opens is not a real scenario to design around yet. Revisit (Q2) if it ever is. |
| D6 | **`AuthResponse` (register/login/refresh) gains a `refreshToken` field, returned in the body in addition to the existing `Set-Cookie`.** Web ignores the field (the cookie still does the job); Android stores it via `androidx.security.crypto` (Keystore-backed) and sends it back in `RefreshRequest.refreshToken`/`LogoutRequest.refreshToken` — the body-accepting side of this `AuthController`/`AuthDtos` already exists today ("non-web clients may send the refresh token in the body") but nothing has ever *returned* one that way. | This is a real, previously-undiscovered gap: without this change a native client cannot complete login at all. Returning it unconditionally (rather than detecting "is this a mobile client" and switching behavior) keeps the auth endpoints client-agnostic — exactly the existing read-side comment's own symmetric intent — and avoids a bug class where a wrong detection heuristic silently breaks one platform. |
| D7 | **`mobile/android/` is its own Gradle root** (own `settings.gradle.kts`, Android Gradle Plugin, Android SDK), not included in the repo's root `settings.gradle.kts` alongside `:backend`/`:web`. | Keeps AGP/Android SDK out of the backend/web contributor toolchain entirely, and means `./gradlew build` at the repo root is unaffected by anything under `mobile/`. CI gets its own path-filtered workflow (§6.7) rather than a job added to the existing `verify` pipeline. |
| D8 | **Retrofit** (not Ktor) for the generated client, per `DESIGN.md` §5.2/§12's own "Retrofit/Ktor" phrasing — this locks that open choice rather than leaving it open twice. OpenAPI Generator's `kotlin` generator, `library=jvm-retrofit2`, `kotlinx-serialization` for (de)serialization. | Retrofit is the more mainstream, better-generator-supported choice for a straightforward REST client with no streaming needs; Ktor's main advantage (Kotlin Multiplatform) is moot since no shared-code-with-iOS plan exists (iOS was dropped — see the ADR 0001/`DESIGN.md` M11+ scoping edits). |
| D9 | **`task_dependency` is out of the sync feed entirely this milestone** (and likely M11.5 too, pending that milestone's own design pass) — no soft delete on that table means a changed-since scan can't represent a removed edge. The Android client (from M11.5 onward) fetches `GET /projects/{id}/dependencies` live whenever a project detail screen is open instead. | Same reasoning as D2's "online-required writes," extended to this one low-value-to-cache, low-cardinality-per-project read. Adding soft-delete to `task_dependency` just to make it sync-able would be a schema change motivated by mobile alone, for a list that's cheap to just fetch live. |
| D10 | **Single Gradle module (`:app`) for hand-written Android code, plus one small generated module (`:openapi-client`)** — package-by-feature inside `:app` (`com.kairon.android.auth`/`.today`/`.todo`/`.account`/`.about`/`.core.*`), not a Gradle module per feature. | Mirrors the backend's own "modular monolith by package, not by Gradle subproject" convention (`CLAUDE.md`) and the web app's single-package `src/features/*` layout — splitting into Gradle modules buys build-parallelism this one-developer app doesn't need yet, at the cost of real ceremony. The generated client stays its own tiny module only because regenerated code should never share a directory with hand-written code (mirrors web's own generated-client separation). |
| D11 | **MVVM**: a Hilt-provided `ViewModel` per screen exposing `StateFlow<UiState>`; a small `Repository` per feature wrapping the Retrofit client + (for `todo`) Room; `SyncRepository` (new, `core.sync`) owns the `/sync` call and fans upserts/tombstones out to each feature's Room DAO. Navigation via Jetpack Navigation-Compose, one `NavHost` in `:app`. | Standard, boring, well-supported Android architecture — nothing here is a novel decision worth debating; picked so implementation time goes to the actual features, not architecture bikeshedding. |
| D12 | **Token refresh is a single-flight OkHttp `Authenticator`** mirroring the web app's `client.ts` 401→refresh→retry wrapper: one in-flight refresh call per process, every other 401'd request awaits it and retries once, a second 401 after a fresh refresh logs the user out. | Reuses a design this codebase has already validated on the web side instead of inventing a second token-refresh strategy; OkHttp's `Authenticator` is the idiomatic place to put this on Android (fires once per 401, before the app's own repositories ever see the failure). |

## 3. Data model

**No new migration.** This milestone's entire backend surface rides on
columns that already exist (`updated_at`, `deleted_at`, `version` — every
mobile-synced table already has them per `DATA_MODEL.md`'s conventions). The
`refresh_token` table is untouched — D6 only changes what `AuthController`
*returns*, not anything stored.

New shared type, `common.sync.ChangeSet<T>` (not persisted — a port-layer
return type, same kind of thing as `TodoApi.PeriodStats`):

```java
package com.kairon.common.sync;

public record ChangeSet<T>(List<T> upserted, List<UUID> deletedIds, boolean truncated) {
}
```

## 4. Backend

### 4.1 New port methods

```java
// todo.api.TodoApi
ChangeSet<TodoItemView> changedSince(UserId userId, Instant since, int limit);

// journal.api.JournalApi
ChangeSet<JournalEntryView> changedSince(UserId userId, Instant since, int limit);

// projects.api.ProjectsApi
ChangeSet<ProjectView> changedSince(UserId userId, Instant since, int limit);
ChangeSet<ProjectTaskView> tasksChangedSince(UserId userId, Instant since, int limit);
```

Each backing repository gains one query that, deliberately, does **not**
filter `deleted_at IS NULL` — the one place in the codebase that needs to see
soft-deleted rows:

```java
// e.g. TodoItemRepository
List<TodoItem> findByUserIdAndUpdatedAtGreaterThanEqualOrderByUpdatedAtAscIdAsc(
        UUID userId, Instant since, Pageable pageable);
```

Each module's service implementation (`TodoService`, `JournalService`,
`ProjectService`/`ProjectTaskService`) follows the same shape:

```java
@Override
@Transactional(readOnly = true)
public ChangeSet<TodoItemView> changedSince(UserId userId, Instant since, int limit) {
    List<TodoItem> rows = repo.findByUserIdAndUpdatedAtGreaterThanEqualOrderByUpdatedAtAscIdAsc(
            userId.value(), since, PageRequest.of(0, limit + 1));
    boolean truncated = rows.size() > limit;
    List<TodoItem> page = truncated ? rows.subList(0, limit) : rows;
    List<TodoItemView> upserted = new ArrayList<>();
    List<UUID> deletedIds = new ArrayList<>();
    for (TodoItem row : page) {
        if (row.isDeleted()) {
            deletedIds.add(row.getId());
        } else {
            upserted.add(mapper.toView(row));
        }
    }
    if (truncated) {
        log.warn("changedSince truncated userId={} since={} limit={}", userId.value(), since, limit);
    }
    return new ChangeSet<>(upserted, deletedIds, truncated);
}
```

### 4.2 `planning.app.SyncService` (new, alongside `PlanningService`)

```java
@Service
@Transactional(readOnly = true)
public class SyncService {

    private final TodoApi todos;
    private final JournalApi journal;
    private final ProjectsApi projects;
    private final Clock clock;
    private final int maxRowsPerType; // kairon.sync.max-rows-per-type, default 500

    public record Snapshot(
            Instant since,                              // cursor for the caller's NEXT call
            ChangeSet<TodoItemView> todos,
            ChangeSet<JournalEntryView> journalEntries,
            ChangeSet<ProjectView> projects,
            ChangeSet<ProjectTaskView> projectTasks) {
    }

    public Snapshot sync(UserId userId, Instant since, Set<SyncType> types) {
        Instant capturedAt = clock.instant();                         // D4 — captured BEFORE any query
        ChangeSet<TodoItemView> todoChanges = types.contains(SyncType.TODO)
                ? todos.changedSince(userId, since, maxRowsPerType) : ChangeSet.empty();
        // ...journal / projects / projectTasks, same pattern, each only queried if requested
        log.debug("Assembled sync snapshot userId={} since={} types={}", userId.value(), since, types);
        return new Snapshot(capturedAt, todoChanges, journalChanges, projectChanges, taskChanges);
    }
}
```

`SyncType` is a small enum (`TODO`, `JOURNAL`, `PROJECT`, `PROJECT_TASK`); the
`types` query param defaults to "all four" when omitted, so M11's Android
client (which only consumes `TODO`) can pass `?types=todo` to skip the other
three queries entirely, and M11.5 just widens the set it asks for — no
backend change needed when that milestone lands.

### 4.3 `planning.web.SyncController` (new, alongside `PlanningController`)

```java
@GetMapping("/sync")
public SyncResponse sync(@CurrentUser UserId userId,
        @RequestParam(required = false) Instant since,
        @RequestParam(required = false) Set<String> types) {
    log.debug("GET /sync userId={} since={} types={}", userId.value(), since, types);
    Instant effectiveSince = since != null ? since : Instant.EPOCH;    // omitted = full bootstrap
    return SyncResponse.from(planningSync.sync(userId, effectiveSince, SyncType.parse(types)));
}
```

`SyncDtos.SyncResponse`/`ChangeSetResponse<T>` mirror `PlanningDtos`'s own
"embed the other modules' `api` DTOs directly, no extra translation" style
(M6 D12) — this module has no domain of its own to translate into either.

### 4.4 `identity` — D6's `AuthResponse` change

```java
// AuthDtos.java
record AuthResponse(
        String accessToken,
        String tokenType,
        long expiresInSeconds,
        String refreshToken,          // NEW — D6; web ignores it, native clients store it
        UserSummary user) {
}
```

`AuthController.register`/`login`/`refresh` all already hold
`result.rawRefreshToken()` (used today only to build the cookie) — passing it
into the response body too is a one-line change at each of the three call
sites, no `AuthService`/`AuthCommands` change needed.

### 4.5 Config

```yaml
kairon:
  sync:
    max-rows-per-type: 500   # D5
```

### 4.6 ArchUnit

No new rule needed. `planning` already has the "no `domain`/`repo`, reads
other modules only through their `api`" shape this reuses exactly; `SyncType`
and `ChangeSet<T>` don't create any new cross-module dependency the existing
rules don't already permit.

### 4.7 Authorization & errors

Every `changedSince` call is scoped by `userId` exactly like every other
query in the codebase (no new authorization surface — there's no "other
user's row" concept for a delta scan, since the `WHERE user_id = ?` is
unconditional). `GET /sync` needs no 404/409 cases at all — an empty
`ChangeSet` for a brand-new user is a perfectly valid response, not an error.

## 5. API contract

Base path `/api/v1`. Bearer access token on every call except `/auth/*`.

| Method & path | Body / params | Response |
| --- | --- | --- |
| `GET /sync` | `since?` (ISO instant, omit for a full bootstrap), `types?` (comma list of `todo,journal,project,projectTask`, default all four) | `200` + `SyncResponse` (always — no error cases, see §4.7) |
| `POST /auth/register` / `/auth/login` / `/auth/refresh` | (unchanged request shapes) | `AuthResponse` — **now also carries `refreshToken`** (D6) |

### `GET /sync` response shape

```json
{
  "since": "2026-10-08T09:15:00Z",
  "todos": {
    "upserted": [ { "id": "018f…", "day": "2026-10-08", "title": "…", "status": "OPEN", "...": "..." } ],
    "deletedIds": ["018f…gone"],
    "truncated": false
  },
  "journalEntries": { "upserted": [], "deletedIds": [], "truncated": false },
  "projects": { "upserted": [], "deletedIds": [], "truncated": false },
  "projectTasks": { "upserted": [], "deletedIds": [], "truncated": false }
}
```

Each `upserted` entry is exactly the same `TodoItemView`/`JournalEntryView`/
`ProjectView`/`ProjectTaskView` shape the existing REST endpoints already
return — so the generated Kotlin models the app already has from those
endpoints are reused as-is for sync, with no second set of "sync" models.

### 6.2 Auth flow

- `TokenStore` (`core.auth`): access token kept **in memory only** (same
  posture as web); refresh token in `androidx.security.crypto`'s
  `EncryptedSharedPreferences` (Keystore-backed), matching `DESIGN.md` §6's
  "Mobile uses the platform secure store" line, which until D6 had no way to
  actually get a token into that store.
- `AuthAuthenticator` (OkHttp `Authenticator`, D12): on a `401`, acquires a
  process-wide mutex, calls `POST /auth/refresh` once with the stored
  refresh token, updates `TokenStore`, and retries the original request; a
  second `401` right after a fresh refresh clears the store and routes to
  Login (refresh-token reuse/expiry — same family-revocation semantics the
  backend already enforces).
- Login/Register screens: plain Compose forms over `AuthRepository`
  (wraps the generated client's auth endpoints); success stores both tokens
  and navigates to Today.

### 6.3 Sync & local cache

- `SyncRepository.sync()` calls `GET /sync?types=todo` (M11 only requests
  `todo` — D3's "ask for what you currently consume" design), persists the
  stored `since` cursor (plain `DataStore` key, not the secure store — it's
  not sensitive), and for each returned `ChangeSet`: upserts into Room,
  deletes by id for every `deletedIds` entry.
- Triggered: on app foreground/resume, after any successful write (§6.4),
  and via a manual pull-to-refresh — no background `WorkManager` sync this
  slice (nothing to reconcile without an offline write queue, D2).
- `todo` Room entity mirrors `TodoItemView` field-for-field (minus
  `deletedAt`, which never reaches the client — tombstones are bare ids).
  `TodoDao` exposes a `Flow<List<TodoItemEntity>>` per day, which `DayView`'s
  `ViewModel` observes directly — Room is the single source of truth the UI
  renders from, never the raw network response (standard single-source-of-
  truth repository pattern).

### 6.4 Writes

Every write (`create`/`patch`/`complete`/`reorder`/`delete`/rollover) calls
the generated client directly; on success the response's own
(already-current) row is upserted into Room immediately — no need to wait
for the next `/sync` tick — and on failure (including "no network") the UI
surfaces a plain error with no retry queue (D2). No client-generated ids are
needed yet for creation (the server still mints them) — that only becomes
necessary once offline *creation* is in scope, a later milestone.

### 6.6 Navigation

One `NavHost` in `:app`, bottom-nav items for every screen that exists in

### 6.7 CI

`android-client` (regenerate), `android-test`, `android-build` — thin
wrappers around the `mobile/android` Gradle wrapper, same spirit as the
existing `be`/`fe` tasks.

## 11. Corrections found during implementation

- **D8's "OpenAPI Generator → Kotlin, `jvm-retrofit2`" needed two fixups to
  actually compile against kotlinx-serialization.** (1) The backend's one
  free-form JSON field (`identity.web.MeDtos`' `Map<String, Object>
  preferences`, embedded in both `MeResponse` and `UpdateMeRequest`) generates
  as `Map<String, kotlin.Any>`, `@Contextual`-annotated — but `@Contextual`
  only replaces a *property's own* serializer lookup, not a generic type
  argument buried inside a `Map`, so the kotlinx.serialization compiler
  plugin fails at compile time with "Serializer for element of type
  kotlin.Any has not been found." `typeMappings`/`importMappings` (the
  documented override) don't reach this case either. Fixed with a small
  `patchGeneratedClient` Gradle task in `:openapi-client`'s own build script
  — runs after `openApiGenerate`, before `compileKotlin` — that rewrites just
  that one field's type to `kotlinx.serialization.json.JsonElement` (which
  has a real built-in serializer) across whichever generated files contain
  it. Still never a hand-edit of checked-in code (D10) since everything under
  `build/generated` regenerates every time. (2) The generated
  `infrastructure/ApiClient.kt` needs `converter-scalars` and
  `logging-interceptor` on `:openapi-client`'s own classpath even though the
  app never calls into that particular generated file directly — added both.
- **A genuinely new backend defect, found only because M11 is the first real
  consumer of the generated OpenAPI spec**: every `@CurrentUser UserId`
  handler parameter was leaking into the spec as a spurious *required* query
  parameter named `userId` (springdoc has no idea it's resolved from the JWT,
  not the query string) — present on literally every authenticated endpoint
  since M7 added springdoc, unnoticed because the web app's hand-written
  client never reads the spec. Fixed by registering
  `SpringDocUtils.getConfig().addAnnotationsToIgnore(CurrentUser.class)` in a
  static initializer on `common.security.WebMvcConfig` (the file that already
  wires `CurrentUserArgumentResolver` into Spring MVC) — out of scope for
  this plan's own §1 "In" list, but a real, previously-undiscovered gap in
  the same spirit as D6's refresh-token gap, so fixed in place rather than
  deferred.
- **AGP 9 (the only version compatible with this environment's Gradle
  9.7.1 — AGP 8.x hits a removed internal Gradle API on Gradle ≥9.6)
  defaults to "built-in Kotlin," which is incompatible with the separate
  `org.jetbrains.kotlin.android` plugin this plan's D8/D10 Kotlin-generator
  tooling (and Hilt's kapt, and Room's kapt) all assume.** Opted out via
  `android.builtInKotlin=false`/`android.newDsl=false` in
  `mobile/android/gradle.properties` rather than adopting the brand-new DSL —
  AGP's own deprecation note says the opt-out is removed in AGP 10 (mid-2026
  per Google's release notes), so this needs revisiting at that point, not a
  one-time fix.
- **KSP's own version numbering has decoupled from Kotlin's** (no KSP release
  yet tracks Kotlin 2.4.20, the latest stable Kotlin at implementation time) —
  used `kapt` for both Hilt's and Room's annotation processing instead of the
  originally-unstated-but-implied KSP, sidestepping that version-matching
  risk entirely. Revisit once KSP catches up; kapt still works today but is
  JetBrains' own deprecated path long-term.
- **D5's `500`-row-per-type cap, Q1/Q2's "unmeasured guess" framing, and D9's
  `task_dependency` sync deferral all held as designed** — no surprises
  there.
- **Q5 resolved**: `minSdk = 26` (as the plan's own leaning suggested),
  `compileSdk`/`targetSdk = 37` — whatever platform happened to already be
  installed locally, paired with `buildToolsVersion = "36.0.0"` (the one
  build-tools version actually present; a slightly older build-tools still
  compiles fine against a newer platform jar). Revisit once a real target-SDK
  policy exists rather than "whatever Android Studio installed."
- Section 9's remaining open questions (Q1-Q4) are unresolved by this
  implementation pass exactly as flagged — none were blocking.
