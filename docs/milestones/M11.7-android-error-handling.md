/# M11.7 — Android: error handling & user feedback — implementation plan

Status: **Accepted — implemented**. Companion to [`../ROADMAP.md`](../ROADMAP.md) (M11.7
acceptance criteria), `backend/.../common/error/` (`ApiException.java`,
`GlobalExceptionHandler.java` — the RFC 7807 shape this plan parses), and
the existing `mobile/android/.../core/network/ApiException.kt`/`ResponseExt.kt`
(the M11-era infra this plan builds on top of, not replaces). Follows the
structure and conventions of
[`M11.6-android-assistant.md`](M11.6-android-assistant.md).

Gap found 2026-10-08 while real-device-testing M11.4's `local` flavor
against a validation error (registering with too short a password): every
Android `ViewModel` that touches the network catches a failure and surfaces
`it.message ?: "<generic fallback>"` — whatever Retrofit's `HttpException`/
OkHttp's own exception happens to put in `.message` (`"HTTP 400 Bad
Request"`, or a bare `SocketTimeoutException` string), never the backend's
actual error body. Confirmed by inspection: the exact
`ex.message ?: "<fallback>"` pattern repeats at **~50 call sites across 16
files** (`AuthViewModels`, `TodoViewModel`, `TodayViewModel`,
`JournalViewModel`, `JournalSearchViewModel`, `ProjectViewModel`,
`ProjectDetailViewModel`, `ProjectFormViewModel`, `ProjectTaskViewModel`,
`AccountViewModel`, `AboutViewModel`, and every `assistant` ViewModel), and
every screen renders whatever string lands there as one bare, unstyled
`Text` with no color/icon/dismiss/retry (`DayViewScreen.kt`'s
`Text(state.error ?: "", ...)` is representative).

*(User decisions locked for this slice — see §2 for the full rationale on
each: errors are categorized from the parsed response body/exception type,
not guessed from `.message` text; validation errors render **inline on the
offending field**; background sync failures get a **non-blocking banner**
over the last-cached Room data, never a full-screen block; foreground
action failures keep today's inline-under-the-action placement but styled
and with real backend text; server errors (5xx) and connectivity failures
get **fixed, Android-owned copy** regardless of whatever text the backend
happened to send, so those two messages stay reliably "try again later" —
every other 4xx shows the backend's own `detail` verbatim, since it is
already deliberately-written, non-technical text. A mutation that 404s
because the row was deleted elsewhere (web, another device) **purges that
row from Room immediately and disables further saving**, rather than
leaving a dead edit form pointed at a row that no longer exists; a
mutation that 409s because the row was *modified* elsewhere gets a
**"Reload" action** that re-fetches the current server copy instead of
just a dead-end message — see D9/D10.)*

---

## 1. Scope

### In

- **A `ProblemDetail` Kotlin DTO + lenient parser** (`core/network/ProblemDetail.kt`)
  for the RFC 7807 body every backend error already sends:
  `type`/`title`/`status`/`detail`/`instance` plus the optional
  `errors: [{field, message}]` array `GlobalExceptionHandler` adds for Bean
  Validation failures. Parses `ApiException.problemBody` (already captured,
  unused today beyond logging) with `Json { ignoreUnknownKeys = true }`;
  returns `null` on any parse failure rather than throwing, so a malformed
  or absent body degrades to the `Unknown` category instead of crashing the
  error-handling path itself.
- **A sealed `AppError` hierarchy + `Throwable.toAppError(): AppError`**
  (`core/network/AppError.kt`) — the single mapping function every call site
  in the app uses from now on, replacing `ex.message ?: "<fallback>"`
  everywhere it appears today (§1 count above). See §2 D1 for the full
  category list and §5.2 for the mapping logic.
- **Fixed, Android-owned copy for exactly two categories** — connectivity
  failures and server errors — chosen deliberately so those two messages
  stay consistent no matter what a given backend failure's own text says
  (D3). Every other category shows the backend's own `detail` (and, for
  validation, each field's own `message`) verbatim.
- **Two small shared Compose components** (`core/ui/ErrorBanner.kt`,
  `core/ui/InlineError.kt`) replacing every screen's own bare `Text` —
  `ErrorBanner` (dismissible, error-colored `Surface`, optional "Retry"
  action) for background sync failures; `InlineError` (icon + error-colored
  text) for foreground action/form failures. Validation's per-field case
  uses `InlineError` reused as the `supportingText` of the offending
  `OutlinedTextField`.
- **A one-shot "session expired" signal** so the login screen can explain
  *why* the user landed there after a forced session clear, distinct from
  an ordinary manual logout (today `AuthAuthenticator`/`SessionClearer`
  already force-clear the session silently — no user-visible explanation
  at all). See D5.
- **Applying the new mapping + components at every one of the ~50 existing
  call sites** (§7 task breakdown groups them by module).
- **Dedicated handling for a mutation that fails because the row is gone or
  stale** — editing/patching/completing/deleting a `todo_item`/
  `journal_entry`/`project`/`project_task`/`project_category` that was
  deleted or modified elsewhere (web, another device) since this device
  last synced it. Confirmed by reading every affected service
  (`TodoService`, `JournalService`, `ProjectService`, `ProjectTaskService`,
  `ProjectCategoryService`): each already does an explicit
  `expectedVersion` check and throws `ApiException.conflict(...)` on a
  stale version, and each row-lookup already filters `deletedAt IS NULL`,
  so a deleted row 404s instead of silently "succeeding." Today, every one
  of those outcomes on an edit screen (confirmed in `ProjectTaskViewModel`
  — on `onFailure`, `error` is set and nothing else happens: Room keeps the
  stale cached row, the Save button stays enabled, there's no way forward
  short of backing out manually) just shows the same flat error text as
  any other failure and leaves the user on a dead screen. See D9/D10.
- Tests: a pure-function `AppErrorMappingTest` covering every category
  (§6), a `ProblemDetailTest` for the parser's lenient/malformed-body
  behavior, a `SessionExpiredSignalTest`, and targeted tests for the
  NotFound/Conflict handling added to `ProjectTaskViewModel`/
  `ProjectFormViewModel`/`JournalEntryViewModel`/`TodoViewModel`.

### Out (deferred, with what picks it up)

- **Any backend change.** `GlobalExceptionHandler`/`ApiException` already
  produce exactly the shape this plan parses (confirmed by reading both
  files) — this is purely an Android-side consumption gap.
- **Retry-with-backoff or offline write queueing.** A "Retry" button on
  `ErrorBanner` just re-triggers the same one-shot action (e.g.
  `syncRepository.sync()` again) — there is no queued/automatic retry
  mechanism, no exponential backoff, and M11 D2's "every write is
  online-required, no offline write queue" stance is unchanged by this
  milestone.
- **M11.8's sync-truncation bug.** A different, already-scoped gap
  (`SyncRepository` advancing the cursor past a `truncated` response) —
  unrelated to how a sync *failure* is reported, which is this plan's whole
  concern.
- **Rewording the backend's own `detail` text.** Confirmed by grep across
  every `ApiException.*(...)` call site in `backend/src/main/java/com/kairon`:
  the existing messages (`"This would create a circular dependency."`,
  `"The resource was modified by another request. Reload and try again."`,
  `"You haven't enabled project editing in Settings."`, etc.) are already
  non-technical and specific. Re-authoring per-type Android copy for these
  would just create a second, drifting source of truth for text the backend
  already owns correctly.
- **A crash-reporting/telemetry pipeline for these errors.** Every failure
  is already logged via `AppLog` at its origin (`ResponseExt.kt`,
  `SyncRepository`, etc.) — this plan changes what the *user* sees, not
  what gets logged.
- **A new single-row `GET /tasks/{id}`-style endpoint.** Confirmed by
  reading `ProjectTaskController`/`TodoController`: neither exposes one
  today (only list/create/patch/delete/reorder) — D10's "Reload" after a
  409 reuses the existing `GET /sync` endpoint plus a Room re-read instead,
  which is both sufficient and consistent with every other "refresh" in
  this app already going through `SyncRepository`.

## 2. Decisions locked for this milestone

| # | Decision | Rationale |
| --- | --- | --- |
| D1 | **`AppError` is a sealed hierarchy with these cases**: `Connectivity` (any `IOException` that never got an HTTP response — timeout, DNS failure, connection refused), `ServerError(status)` (HTTP 5xx), `Validation(fieldErrors: List<FieldError>)` (400 with a non-empty `errors[]`), `LoginRejected(detail)` (401 specifically from `/auth/login` or `/auth/register`), `SessionExpired` (set directly by the auth layer on a forced clear, never parsed from a body — see D5), `NotFound(detail)` (HTTP 404 — see D9), `Conflict(detail)` (HTTP 409 — see D10), `Domain(detail)` (any other `ApiException` carrying a `detail` — 400/403/422/429), `Unknown` (unparseable body, or a throwable that's neither `IOException` nor `ApiException`). | Mirrors the real shapes the backend actually produces (confirmed via `GlobalExceptionHandler`/`ApiException.java`) rather than an abstract guess — every category maps to something the client can actually distinguish (exception type, HTTP status, body shape), never to sniffing `.message` text. 404 and 409 get their own cases rather than folding into `Domain` because, unlike a generic 400/403/422/429, both carry a concrete, uniform follow-up action the UI should take (D9/D10), not just text to display. |
| D2 | **The category is derived from the exception type + parsed body, never from string-matching `.message`.** `IOException` (not already wrapped as `ApiException`) → `Connectivity`. `ApiException` → branch on `httpStatus`: `>= 500` → `ServerError`; `400` with `errors` non-empty → `Validation`; `401` → `LoginRejected` if the call's own `event` tag is `"login"`/`"register"` (the only two call sites that ever throw a *login-rejection* 401 — any other 401 reaching a ViewModel today already means `AuthAuthenticator`'s refresh gave up, which goes through D5's path instead, never through this mapping); `404` → `NotFound`; `409` → `Conflict`; everything else with a non-blank `detail` → `Domain`; otherwise → `Unknown`. | A `.message`-text heuristic is exactly the thing this milestone exists to remove — it's fragile (wording changes silently break it) and was never correct for non-English-shaped `.message` values like `"timeout"`. Branching on status + a lenient-parsed, versioned response shape is the stable alternative. |
| D3 | **`Connectivity` and `ServerError` get fixed, Android-owned copy — the backend's own `detail` is ignored for these two.** `Connectivity` → *"Couldn't connect to the server. Check your connection and try again."* (sync-context callers append *"Showing your last saved data."*). `ServerError` → *"Kairon's server ran into a problem. Please try again later."* *(User decision — the explicit requirement this milestone started from.)* | A connectivity failure has no backend body at all, so there's nothing to show regardless. A 5xx's `detail` today is a generic, scheduler-dependent string (`"An unexpected error occurred."` from `GlobalExceptionHandler.handleUnexpected`, but could in principle be something else from a future handler) — pinning the copy here guarantees the user always gets the specific "try again later" framing that was asked for, rather than inheriting whatever a given 500 path happens to say. Every *other* category (D1's `Domain`/`Validation`/`LoginRejected`/`NotFound`/`Conflict`) shows the backend's real `detail`, since those are deliberately-authored and specific (§1 "Out") — `NotFound`/`Conflict` additionally trigger D9/D10's own follow-up behavior, not just text. |
| D4 | **Validation errors render inline, per field** — `AppError.Validation.fieldErrors` is a `List<FieldError(field, message)>`; each form matches entries by field name to its own Compose field and passes `message` as that field's `supportingText` (styled via `InlineError`/`isError`). A field error with no matching UI field in that form (shouldn't normally happen — forms declare the same field names the backend validates) falls back to one summary `InlineError` line joining the orphaned messages. *(User decision.)* This reaches `LoginScreen`/`RegisterScreen`, not just the project forms: `AuthDtos.LoginRequest` is itself `@Email @NotBlank` on `email` and `@NotBlank` on `password` (confirmed by reading `AuthDtos.java`), so a malformed email or blank field on *login*, not just registration, can come back as a 400 with `errors[]` — today that's indistinguishable from a wrong-password 401, both collapsing into the same flat string. | Matches the ROADMAP's own stated leaning now that the data to do it right exists (`errors[]` was always present server-side; nothing before this milestone ever parsed it). Precise, per-field feedback for a login/register/project-task form rather than one generic blob. |
| D4a | **A wrong-password/wrong-email 401 (`AppError.LoginRejected`) is deliberately never attributed to either the email or password field** — it renders as one line below both fields (today's existing placement), same text either way. | The backend's own `AuthService` intentionally returns the identical `"Invalid email or password."` for both "no such email" and "right email, wrong password" (confirmed: both branches in `AuthService.java` throw `ApiException.unauthorized(INVALID_CREDENTIALS)` with the same constant) specifically so a guesser can't enumerate valid emails by noticing which field an error attaches to. Pinning this message to one field on the client would quietly undo that. |
| D5 | **A new one-shot session-expired signal, not parsed from any response body.** `AuthAuthenticator` already knows exactly when it force-clears a session (two paths today: `"secondUnauthorized"` — a retried request still 401'd — and `"refreshRejected"`/`"noRefreshTokenStored"` inside `refreshAccessToken()`); each of those call sites, immediately before/alongside calling `sessionClearer.clearSession()`, now also emits onto a new app-scoped `SessionExpiredSignal` (a `MutableSharedFlow<Unit>(replay = 0, extraBufferCapacity = 1)` singleton). `LoginScreen` collects it once (`LaunchedEffect`) and shows `AppError.SessionExpired`'s fixed copy — *"Your session has expired. Please log in again."* — as a one-time `InlineError`/snackbar; an ordinary manual "Log out" tap (`AuthRepository.logout`) never touches this signal, so it reaches the login screen with no such message. | Today a forced session clear is entirely silent from the user's point of view — `SessionViewModel.signedIn` flips false, the nav host reactively routes to the login screen (existing M11 infra, unchanged by this plan), and the user is left to wonder why they were logged out. The *cause* (refresh rejected/exhausted) is known precisely at the one place it happens (`AuthAuthenticator`) and is cheap to thread through as a signal rather than trying to reconstruct "was this 401 a forced-logout 401" later from a response body that, for an expired-JWT 401, usually doesn't even carry a custom `detail` (it comes from Spring Security's own entry point, not `ApiException.unauthorized`). |
| D6 | **Background sync failures never block the screen** — `SyncRepository.sync()`'s `Result` failure, wherever a `ViewModel` calls it (`TodoViewModel.refresh`, `TodayViewModel`, `JournalViewModel`, `ProjectViewModel`, etc.), maps to an `AppError` shown via `ErrorBanner` *above* the existing Room-backed list content, which keeps rendering whatever was last synced. The banner carries a "Retry" action that just re-invokes the same `refresh()`/`sync()` call. *(User decision.)* | Matches this app's offline-first architecture (Room is already the source of truth every list screen renders from, confirmed across `TodoViewModel`/`ProjectViewModel` etc.) — a transient network hiccup shouldn't make cached data briefly inaccessible, which is what today's "one `error` field, same rendering path as everything else" pattern risks once that field is populated with no distinction from a foreground action failure. |
| D7 | **Foreground action failures (quick-add, complete, patch, reorder, rollover, project/task/category CRUD, dependency add/remove, every assistant accept/dismiss/generate call) keep today's "surface in this screen's own `error` state field" placement**, just restyled via `InlineError` and populated from `toAppError()` instead of `.message`. No new banner/dialog plumbing for these — only the *content* and *look* of the existing error slot changes. | These already interrupt a specific user-initiated action in place (e.g. "failed to add todo" appears right where the quick-add was) — unlike a background sync, there's no "last-known-good state" to protect by not blocking, so the existing placement is already correct; only the message and its visual treatment were wrong. Keeps this milestone's surface area to a mapping function + two small components + call-site updates, not a UI-architecture rework. |
| D8 | **No new Gradle dependency.** `kotlinx-serialization-json` (for `ProblemDetail`), JUnit, and MockK are already declared (`app/build.gradle.kts`); the two new Compose components use only Material3 primitives already in use everywhere else. | Confirmed by inspection of `app/build.gradle.kts` — this milestone is additive Kotlin/Compose files plus edits to existing call sites, not new tooling. |
| D9 | **A mutation (`patch`/`complete`/`delete`) that returns `AppError.NotFound` purges that row from Room immediately** (`<dao>.deleteById(id)` — already exists on every affected DAO, used today on the *success* path of an explicit delete) **rather than waiting for the next `/sync`.** On a dedicated edit screen (`TaskEditScreen`/`ProjectFormScreen`/`JournalEntryScreen`), the Save button is disabled once this happens (a new `gone: Boolean` field on that screen's own UI state) — resubmitting a patch against a row that's already confirmed gone can only 404 again. The user is **not** force-navigated away; the message (D3's "show the backend's `detail` verbatim" policy — already "Task not found."/"Todo item not found."/etc., clear enough as-is) stays in the screen's existing error slot until they back out themselves. For `TodoViewModel`'s inline (non-screen) patch/complete actions, there's no "Save button" to disable — purging the Room row is itself the user-visible fix, since the day list renders straight from Room and the stale item simply disappears. | Confirmed real and reachable, not hypothetical: every one of `TodoService`/`JournalService`/`ProjectService`/`ProjectTaskService`/`ProjectCategoryService`'s row-lookups already filters `deletedAt IS NULL`, so a concurrently-deleted row 404s on the next edit attempt from this device — and confirmed as a live gap: `ProjectTaskViewModel`'s `onFailure` (and every sibling ViewModel's) today does nothing but set `error`, leaving Room's stale copy in place and the Save button enabled, i.e. a dead end that just 404s again on retry. Not force-navigating away was a deliberate simplicity call — it avoids a new one-shot nav/snackbar-after-pop signal (the same category of plumbing D5 already had to add for session expiry, not worth a second instance for this) in favor of reusing the error slot and UI state this milestone already builds for every other case. |
| D10 | **A mutation that returns `AppError.Conflict` shows the backend's own message (already clear — e.g. `"This task was modified by another request. Reload and try again."`) plus a "Reload" action**, extending `InlineError` with an optional `actionLabel`/`onAction` pair rather than adding a third visual treatment alongside it and `ErrorBanner`. For the four Room-backed, sync-fed edit screens (`ProjectTaskViewModel`, `ProjectFormViewModel`, `JournalEntryViewModel`, and `TodoViewModel`'s inline patch/complete), Reload calls the existing `SyncRepository.sync()` and then re-reads that one row from Room — for the three dedicated-screen ViewModels, the fresh row's fields (and new `version`) overwrite the form's own local state, discarding the user's unsaved edits; for `TodoViewModel`'s inline case, nothing else is needed since the day list already renders straight from Room. **Categories are the one exception**: `project_category` is confirmed not sync-fed (per `CLAUDE.md`'s own "no entity for `ProjectCategory`... neither is sync-fed"), so `ProjectViewModel`'s category rename/reorder functions instead Reload by re-calling the existing live `GET /project-categories` list endpoint and replacing the in-memory category list state — no Room involved either way. Reload never asks for confirmation before discarding unsaved edits — tapping it *is* the confirmation, matching this app's existing no-confirmation posture for every other destructive-ish action except journal-reflection opt-in. | Confirmed real and reachable the same way as D9: all five of those services do their own explicit `expectedVersion` check (not just relying on a generic JPA optimistic-lock exception) and throw the same `ApiException.conflict(...)` shape. Unlike `NotFound`, the row still exists here, so there's a meaningful "try again" action to offer rather than a dead end — and since there's no single-row `GET` endpoint anywhere in this API (§1 "Out"), reusing `/sync` (already idempotent, already cheap, already what every "refresh" in this app does) is simpler than adding one just for this. |

## 3. Data model

**None — no backend, no Room, no DataStore change.** `ProblemDetail` is a
transient parse of an existing response body already flowing through the
app (`ApiException.problemBody`); `SessionExpiredSignal` is an in-memory
`SharedFlow` with no persistence (a process restart has no "was mid-expiry"
state to recover — the next failed-refresh attempt, if any, emits fresh).

### 5.2 `AppError` mapping (`toAppError`)

```kotlin
sealed interface AppError {
    data object Connectivity : AppError
    data class ServerError(val status: Int) : AppError
    data class Validation(val fieldErrors: List<FieldError>) : AppError
    data class LoginRejected(val detail: String) : AppError
    data object SessionExpired : AppError
    data class NotFound(val detail: String) : AppError   // D9
    data class Conflict(val detail: String) : AppError   // D10
    data class Domain(val detail: String) : AppError
    data object Unknown : AppError
}

data class FieldError(val field: String, val message: String)

fun Throwable.toAppError(isLoginOrRegister: Boolean = false): AppError = when (this) {
    is ApiException -> when {
        httpStatus >= 500 -> AppError.ServerError(httpStatus)
        else -> {
            val problem = ProblemDetail.parse(problemBody)
            val fieldErrors = problem?.errors
            val detail = problem?.detail
            when {
                httpStatus == 400 && !fieldErrors.isNullOrEmpty() ->
                    AppError.Validation(fieldErrors.map { FieldError(it.field, it.message) })
                httpStatus == 401 && isLoginOrRegister ->
                    AppError.LoginRejected(detail ?: "Invalid email or password.")
                httpStatus == 404 && !detail.isNullOrBlank() -> AppError.NotFound(detail)
                httpStatus == 409 && !detail.isNullOrBlank() -> AppError.Conflict(detail)
                !detail.isNullOrBlank() -> AppError.Domain(detail)
                else -> AppError.Unknown
            }
        }
    }
    is IOException -> AppError.Connectivity
    else -> AppError.Unknown
}

fun AppError.userMessage(): String = when (this) {
    AppError.Connectivity -> "Couldn't connect to the server. Check your connection and try again."
    is AppError.ServerError -> "Kairon's server ran into a problem. Please try again later."
    is AppError.Validation -> fieldErrors.joinToString("\n") { it.message } // per-field use reads fieldErrors directly
    is AppError.LoginRejected -> detail
    AppError.SessionExpired -> "Your session has expired. Please log in again."
    is AppError.NotFound -> detail  // D9 — already clear as-is ("Task not found.", etc.)
    is AppError.Conflict -> detail  // D10 — already clear as-is ("...Reload and try again.")
    is AppError.Domain -> detail
    AppError.Unknown -> "Something went wrong. Please try again."
}
```

`isLoginOrRegister` is passed `true` only from `LoginViewModel`/
`RegisterViewModel`'s own `onFailure` — every other call site uses the
default, so a stray 401 elsewhere never gets misread as a credentials
rejection (D2).

### 5.3 `SessionExpiredSignal` wiring (D5)

- `AuthAuthenticator.authenticate()`'s `"secondUnauthorized"` branch and
  `refreshAccessToken()`'s `"refreshRejected"`/`"noRefreshTokenStored"`
  branches each call `sessionExpiredSignal.notifyExpired()` immediately
  before/alongside `sessionClearer.clearSession()`.
- `LoginScreen` (reached automatically once `SessionViewModel.signedIn`
  flips false — unchanged nav-host behavior) collects the signal once via
  `LaunchedEffect(Unit) { sessionExpiredSignal.events.collect { ... } }`
  and shows `AppError.SessionExpired.userMessage()` via `InlineError`,
  cleared on the next login attempt.
- A manual "Log out" (`AuthRepository.logout`/`logoutAll`) never emits this
  signal — it calls `sessionClearer.clearSession()` directly, same as
  today, with no explanation needed on the resulting login screen.

### 5.4 Call-site updates

Every `*ViewModel` whose own UI state only ever shows one flat error line —
every file in §1's count **except** `AuthViewModels.kt` (see below) —
changes from:

```kotlin
.onFailure { ex -> error.value = ex.message ?: "Failed to add todo" }
```

to:

```kotlin
.onFailure { ex -> error.value = ex.toAppError().userMessage() }
```

(`TodoViewModel.refresh`/`TodayViewModel`'s sync-triggering functions route
through `ErrorBanner` instead of the plain `error` field per D6 — see §7 for
the exact per-screen split.)

**`AuthViewModels.kt`/`LoginScreen`/`RegisterScreen` are the one exception**
to the flatten-to-`String` treatment above, per D4/D4a: collapsing a
`Validation` case into `userMessage()`'s joined string here would silently
defeat the one place per-field placement matters most. `AuthUiState.Error`
therefore carries the `AppError` itself, not a `String`:

```kotlin
sealed interface AuthUiState {
    data object Idle : AuthUiState
    data object Loading : AuthUiState
    data object Success : AuthUiState
    data class Error(val error: AppError) : AuthUiState
}
// ...
.onFailure { _state.value = AuthUiState.Error(it.toAppError(isLoginOrRegister = true)) }
```

`LoginScreen`/`RegisterScreen` then render per-field:

```kotlin
val fieldError = { field: String ->
    (state as? AuthUiState.Error)?.error
        ?.let { it as? AppError.Validation }
        ?.fieldErrors?.firstOrNull { it.field == field }?.message
}
OutlinedTextField(
    value = email, onValueChange = { email = it }, label = { Text("Email") },
    isError = fieldError("email") != null,
    supportingText = fieldError("email")?.let { { Text(it) } },
)
OutlinedTextField(
    value = password, onValueChange = { password = it }, label = { Text("Password") },
    isError = fieldError("password") != null,
    supportingText = fieldError("password")?.let { { Text(it) } },
)
val formLevelError = (state as? AuthUiState.Error)?.error?.let {
    if (it is AppError.Validation) null else it.userMessage() // D4a: LoginRejected/Connectivity/etc. render here, never field-attributed
}
formLevelError?.let { InlineError(it) }
```

### 5.5 `ErrorBanner` / `InlineError`

- `ErrorBanner(message: String, onRetry: (() -> Unit)?, onDismiss: () -> Unit)`
  — a `Surface` using `MaterialTheme.colorScheme.errorContainer`, an icon,
  the message, and an optional "Retry" `TextButton`; placed once at the top
  of each sync-backed list screen's content, driven by a new
  `syncError: AppError?` field alongside each affected `ViewModel`'s existing
  `error`/`syncing` state.
- `InlineError(message: String, actionLabel: String? = null, onAction: (() -> Unit)? = null, modifier: Modifier = Modifier)`
  — a `Row` with an error icon + `Text` in `MaterialTheme.colorScheme.error`,
  plus an optional trailing `TextButton(actionLabel)` when both action
  params are non-null. Used as a standalone replacement for every bare
  `Text(state.error)` call; for `AppError.Validation`, passed per-field (no
  action) as a form field's `supportingText` (`isError = true`); for
  `AppError.Conflict` (D10), passed with `actionLabel = "Reload"`.

### 5.6 CI

### 5.7 Handling a mutation against a since-deleted or since-modified row (D9/D10)

Applies to every `onFailure` in `ProjectTaskViewModel.save`/`delete`,
`ProjectFormViewModel.save`, `JournalEntryViewModel.save`/`delete`, and
`TodoViewModel`'s `patch`/`complete`/`delete`/`reorder` functions — i.e.
every mutation against a row this device had previously cached.

```kotlin
.onFailure { ex ->
    when (val appError = ex.toAppError()) {
        is AppError.NotFound -> {
            projectTaskDao.deleteById(id)       // same call already used on a successful delete
            _state.value = _state.value.copy(saving = false, error = appError, gone = true)
        }
        is AppError.Conflict -> {
            _state.value = _state.value.copy(saving = false, error = appError) // "Reload" wired below
        }
        else -> _state.value = _state.value.copy(saving = false, error = appError)
    }
}
```

- **The three dedicated edit-form screens** (`TaskEditScreen`,
  `ProjectFormScreen`, `JournalEntryScreen`) add one `gone: Boolean = false`
  field to their UI state (D9); the Save `Button`'s `enabled` expression
  gains `&& !state.gone`. No navigation change — the user backs out with
  the screen's existing back arrow whenever they're ready.
- Each of those three ViewModels gains a `reload()` function for the
  `AppError.Conflict` case's "Reload" action (D10):
  `syncRepository.sync()`, then re-read this one row from its own DAO
  (`projectTaskDao.listForProject(projectId).firstOrNull { it.id == taskId }`,
  mirroring the exact lookup the screen's own `init` block already does)
  and overwrite the form's local state (including `version`) with the
  fresh copy, clearing `error`.
- **`TodoViewModel`'s inline actions** need neither `gone` nor a bespoke
  `reload()` — `NotFound` purges the Room row directly (the day list,
  Room-observed, drops the item on its own); `Conflict`'s "Reload" action
  is just `refresh()` (the same function the screen's own pull-to-refresh
  already calls), since there's no separate form state to repopulate.
- **`ProjectViewModel`'s category functions** (rename/reorder/delete) follow
  the same `NotFound`/`Conflict` branches but never touch Room (categories
  aren't sync-fed — §1 "Out"): `NotFound` removes the category from the
  in-memory list state directly; `Conflict`'s "Reload" re-calls
  `categoryApi.list()` and replaces that state wholesale.

## 10. Corrections found during implementation

- **D6's banner treatment only applies to the three `ViewModel`s that
  actually inject `SyncRepository`** — `TodoViewModel`, `JournalViewModel`
  (day view), and `ProjectDetailViewModel`. `TodayViewModel.refresh()` calls
  `PlanningControllerApi.today()` directly (no Room cache behind it — its
  `dueProjectTasks`/`hasJournalEntry` live only in UI state) and
  `ProjectViewModel.refresh()` is a plain live double-fetch (categories +
  projects, never Room-backed either) — both stay on D7's plain inline
  treatment, since there's no "last-synced cached data" for a banner to
  protect in either case. §2 D6's own "wherever a ViewModel calls it
  (TodoViewModel.refresh, TodayViewModel, JournalViewModel, ProjectViewModel,
  etc.)" overstated this — confirmed by reading all four constructors.
- **`ProjectViewModel`'s `error` field became `AppError?`** (not left as
  `String?`) so its category rename/reorder/delete functions (D10) can offer
  a "Reload" action the same way every other D9/D10 `ViewModel` does; a new
  `reloadCategories()` re-fetches just `GET /project-categories`, matching
  D10's own description. Every other `ProjectViewModel` function
  (`refresh`/`deleteProject`/`changeStatus`/`reorderProjects`/`createCategory`)
  just stores the mapped `AppError` with no special NotFound/Conflict
  handling — D10 only ever asked for that on the category functions.
- **`Icons.Filled.Error` doesn't exist in this app's `material-icons-core`
  dependency** (confirmed by inspecting the artifact's own class list) —
  `ErrorBanner`/`InlineError` use `Icons.Filled.Warning` instead, which is
  present. D8's "no new Gradle dependency" still holds for the icon.
- **One new test-only dependency, `mockk-android`** (`androidTestImplementation`,
  same version as the existing `mockk`), added for `LoginScreenTest` — a
  genuine exception to D8. There was no `androidTest` source set in this
  project before this milestone (confirmed: `app/build.gradle.kts` already
  declared `androidTestImplementation(libs.compose.ui.test.junit4)` plus a
  `debugImplementation` of `ui-test-manifest`, but no `src/androidTest`
  directory existed), and the plain JVM `mockk` artifact doesn't work
  against real Android bytecode running on-device/emulator — `mockk-android`
  is the standard substitute for instrumented tests. Justified by §6's own
  testing table asking for a real Compose UI test of `LoginScreen`'s D4/D4a
  per-field placement, not just the pure-function `AppErrorMappingTest`.
- **The new `core/ui/ErrorBannerTest.kt`/`InlineErrorTest.kt`/
  `auth/LoginScreenTest.kt` compile cleanly** (`:app:compileLocalDebugAndroidTestKotlin`)
  but were **not run on a device or emulator** — none was attached in the
  implementation environment (`adb devices` returned empty). Run
  `:app:connectedAndroidTestLocalDebug` against a real device/emulator
  before merging to confirm they pass for real, not just compile.
  `RegisterScreen` didn't get an equivalent dedicated test — it shares the
  exact same per-field/form-level rendering pattern `LoginScreenTest`
  already exercises, so the marginal coverage didn't seem worth a second,
  near-identical test file; revisit if `RegisterScreen`'s own rendering ever
  drifts from `LoginScreen`'s.
- **`TodoDao`/`JournalDao`/`ProjectTaskDao`'s `deleteById` in a D9 branch is
  invoked from inside `.onFailure {}`, not awaited inline** (`viewModelScope.launch
  { todoDao.deleteById(id) }` rather than a direct `suspend` call) in the few
  spots where the enclosing lambda itself isn't a `suspend` context — this
  does mean the Room delete and the `_state`/`error` update aren't
  guaranteed to land in the same frame, though both still happen on the
  same `viewModelScope` and complete essentially immediately in practice.
  Flagged here rather than "fixed" because restructuring every one of those
  call sites to guarantee strict ordering would have meant a wider
  refactor of each `ViewModel`'s existing `runCatching { }.onFailure { }`
  shape than this milestone's scope — revisit only if a real race surfaces.
