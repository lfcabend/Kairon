# M11.8 — Android: sync truncation correctness — implementation plan

Status: **Accepted — implemented**. Companion to [`../ROADMAP.md`](../ROADMAP.md)
(M11.8 acceptance criteria) and `mobile/android/.../core/sync/SyncRepository.kt`/
`SyncCursorStore.kt` (the M11-era infra this plan builds on top of, not
replaces). Much smaller in scope than M11.7 — one file's control flow plus
its test, not a cross-cutting sweep — so this plan skips that file's
heavier section structure where it would just restate the obvious.

Gap found 2026-10-08 while fixing a cross-account data leak (the Android app
wasn't wiping Room/the `/sync` cursor on logout). That fix makes every login
start a full resync from `since=null`, which made this pre-existing,
previously unlikely-to-bite gap considerably more likely to actually surface:
`GET /sync` caps each type at `kairon.sync.max-rows-per-type` rows (default
500, oldest-`updatedAt`-first) and sets that type's `truncated` flag instead
of returning the rest (`planning.app.SyncService`/`SyncProperties`, M11 D5;
already named as an open question in M11-android-foundation.md Q2), but
`SyncRepository.sync()` wrote the response's own `since` (`capturedAt` — read
*before* the underlying queries run, M11 D4) into `SyncCursorStore`
unconditionally, never checking `truncated`. For an account with more than
500 rows of a given type, the oldest rows past the cap would never sync down
to that device again — the cursor had already jumped to "now."

---

## 1. Decision locked for this milestone

| # | Decision | Rationale |
| --- | --- | --- |
| D1 | **The retry loop runs inline, blocking the calling `sync()` suspend function, with no separate "catching up" UI state.** `sync()` repeats the `GET /sync` call, each round's `since` advanced to the newest `updatedAt` actually seen among that round's own upserted rows (never the response's own `since`, which is "now" and would skip the untouched remainder — the same mistake this milestone fixes), until a round comes back with every requested type non-truncated; only then is `SyncCursorStore` written. | Matches this app's existing "every write is online-required, no background queue" posture (M11 D2) and keeps the change to one function's control flow. A background "catching up" progress UI is real added complexity (a new state surface on every screen that triggers a sync) that isn't justified before a real account's row counts make a single login-time resync noticeably slow — nothing in this app today approaches 500 rows of one type. Revisit if that changes. |
| D2 | **No real per-type keyset `nextCursor` is added.** The retry's `since` is derived from the plain `updatedAt` already present on every upserted row the client receives — not a new, opaque server-issued cursor. A round whose truncated page contains only tombstones (`ChangeSet.deletedIds`, which carry no `updatedAt`) can't be advanced past this way; `sync()` fails loudly in that case (a clear exception, caught by the existing `runCatching`/`Result` wrapping, same as any other sync failure) rather than reissuing an identical request forever. | `ChangeSet<T>` deliberately doesn't echo an `updatedAt` for a deleted id (soft deletes don't echo the deleted row's own fields, by design — see `ChangeSet`'s own doc comment) and nothing scoped for this milestone adds one. A real keyset cursor was already flagged as deferred at M11 design time (Q2) and stays deferred — building one now, before this gap has ever actually been observed in practice (every account's tombstone volume is tiny relative to 500), would be solving a problem that doesn't yet exist. The fail-loud fallback keeps the known gap *visible* (a logged, reported failure) instead of silently reintroducing the exact "old rows never sync down" bug this milestone exists to close. |
| D3 | **A fixed `MAX_ROUNDS = 50` bounds the loop** as a pure safety net against a genuine non-convergence bug, never expected to be hit — each round either makes forward progress (D1) or fails fast (D2). | Cheap insurance against an infinite loop reaching production if some future change breaks the progress invariant; 50 rounds × 500 rows is already far beyond any real account's size. |

## 2. Data model / backend

**None.** `GET /sync`'s `ChangeSet`/`truncated` contract (`planning.app.SyncService`,
`common.sync.ChangeSet`) is unchanged — this is purely an Android-side
consumption gap, the same shape of fix M11.7 was for error handling.

## 3. Android

`core/sync/SyncRepository.kt`'s `sync()` now loops:

```kotlin
var since = effectiveSince
while (true) {
    val response = syncApi.sync(since, REQUESTED_TYPES.joinToString(","))
    val body = response.bodyOrThrow(TAG, "sync")
    // ...upsert/delete into each DAO, as before...
    // track anyTruncated across all four ChangeSets, and maxSeenUpdatedAt
    // across every upserted row's own updatedAt (seeded from `since`)
    if (!anyTruncated) {
        cursorStore.write(body.since)
        cursorStore.writeSyncedTypes(REQUESTED_TYPES.toSet())
        break
    }
    check(maxSeenUpdatedAt != since) { "no forward progress available" } // D2
    since = maxSeenUpdatedAt
}
```

No new files, no new Gradle dependency. `SyncCursorStore` is unchanged — the
fix is entirely about *when* `sync()` calls `cursorStore.write`, not the
store's own shape.

## 4. Testing

`SyncRepositoryTest` gains two cases (existing cases all still pass
unchanged — the single-round, non-truncated path is exactly the same control
flow as before):

- `aTruncatedPageIsFollowedByARetryUntilEveryTypeIsNonTruncated` — the
  roadmap's own requested repro: a first `todos` response truncated with two
  rows, a second call (asserted via `coEvery` to be invoked with `since`
  equal to the first page's own newest `updatedAt`, not the first response's
  `since`) returning the remaining row non-truncated; asserts both pages'
  rows reach `todoDao.upsertAll` and the cursor is written exactly once, with
  the *second* round's `since`, never the first's.
- `aTruncatedPageOfOnlyTombstonesFailsInsteadOfLoopingForever` — D2's known
  gap: a truncated page with upserts empty and only `deletedIds` populated
  makes `sync()` return `Result.failure` without writing the cursor, rather
  than reissuing the identical request forever.

Ran via `:app:testLocalDebugUnitTest --tests
"com.kairon.android.core.sync.SyncRepositoryTest"` — all 9 cases (7 existing
+ 2 new) pass.
